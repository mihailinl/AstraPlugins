# Разрешения — нормативная спецификация

> Перевод. Источник истины — [docs/en](../../en/spec/permissions.md); при расхождении верна английская версия.

**Статус:** нормативно. Словарь, шлюз, потолки, четыре пути происхождения
и хеш — всё это реализовано и применяется; там, где что-то специфицировано,
но ещё не применяется, этот документ говорит об этом в соответствующей
строке.

Слова требований — в духе RFC 2119.

В `plugin.toml` есть два ортогональных раздела, и путать их — это как раз
тот баг, для исправления которого создан этот словарь:

| раздел | направление | вопрос |
|---|---|---|
| `[capabilities]` | демон → плагин | *что я реализую, что Astra может вызвать внутри?* |
| `[permissions]` | плагин → демон | *что я могу вызывать наружу, и какие поверхности мне могут выдать?* |

Раньше для двух вещей было одно слово, и слово значило первую — именно
так `dom_access` оказался возможностью, которую плагин выдавал сам себе,
просто объявив её.

---

## 1. Словарь

Восемь id, закрытый набор (`astra-plugin-manifest/src/permissions.rs`,
`PERMISSION_NAMES`, закреплённый за enum тестом). Реестр валидирует id
заявки против этого списка, а таблица локализованных меток Astra
проиндексирована по нему, так что id, добавленный в одном месте и не
добавленный в остальных, отрисуется как пустая строка.

| id | закрывает | что даёт | высокий риск |
|---|---|---|---|
| `fire_trigger` | `PluginHostService.FireTrigger` | запускать сохранённые автоматизации пользователя | |
| `subscribe_events` | `SubscribeEvents` | получать события демона, **ограничено объявленными типами** (§1.1) | |
| `set_variable` | `SetVariable` | писать в контекст переменных демона, в пространстве имён вызывающего плагина | |
| `send_chat_message` | `SendChatMessage` | управлять ходом ИИ — тратить токены пользователя, говорить голосом его ассистента | ● |
| `push_to_ui` | `PushToUi` | отправлять событие в окно Astra | ● |
| `set_theme_contribution` | `SetThemeContribution` | переоформлять всё приложение | ● |
| `dom_access` | *нет RPC* — **поверхность** | выполнять собственный скрипт плагина внутри окна Astra, с доступом к беседам пользователя и интерфейсу любого другого плагина | ● |
| `client` | *нет RPC* — **поверхность** | выступать фронтендом клиента: собственная поверхность чата, собственная сессия | ● |

**Пять помеченных ● высокорисковые** (`HIGH_RISK_PERMISSIONS`), и каждое
получает свой чекбокс согласия. §4.3 плана перечисляет четыре чекбокса и
пропускает `push_to_ui`; §5.6 перечисляет пять. Реализация берёт
**объединение**, потому что расхождение — между параграфом UI и разделом
безопасности, а лишний чекбокс стоит клика, тогда как недостающий стоит
самого свойства.

**`dom_access` и `client` не закрывают ни один RPC**, и именно поэтому им
нужна вторая точка применения: они применяются там, где выдаётся сама
*поверхность* (§4.2), а не там, где отвечают на вызов.

### 1.1 Аргументы разрешений

Запись `[permissions]` — это объект, не булево значение:

```toml
[permissions]
fire_trigger     = { reason = "Fires the on_dice_roll trigger you configure" }
subscribe_events = { types = ["command_completed"], reason = "Reacts when a command finishes" }
set_variable     = { scopes = ["plugin"] }
```

| член | тип | значение |
|---|---|---|
| `reason` | строка, ≤ 140 символов | собственные слова автора (§6) |
| `types` | массив строк | **только `subscribe_events`.** Список разрешённых типов событий |
| `scopes` | массив строк | **только `set_variable`.** `plugin` / `session` / `persistent`. **Зарезервировано** — демон сегодня разделяет по пространству имён каждую запись плагина по его id, так что это пока ничего не сужает. Разбирается, чтобы манифест, объявляющий это, был публикуем и хешировался одинаково везде |

**`subscribe_events.types` — это список разрешённого, применяемый
демоном для каждого события, и пустой не разрешает ничего.** Три
состояния, и среднее — вся суть:

* разрешения нет → вообще нет потока;
* разрешение есть, `types` пуст → **не разрешает ничего**; демон
  отклоняет подписку с сообщением, называющим решение, а не отдаёт
  поток, который вечно молчит;
* `types` перечислены → ровно эти значения `AstraEvent::event_type_str()`.

Интуитивное прочтение — «нет фильтра значит всё» — это именно та дыра,
для закрытия которой существует это разрешение: неотфильтрованный
подписчик получает `speech_recognized`, а это каждое слово, которое
говорит пользователь.

### 1.2 Неизвестные id сохраняются, а не отклоняются

Манифест, называющий id, о котором эта сборка никогда не слышала,
**принимается**. Две причины, и обе указывают в одну сторону:

1. **Прямая совместимость.** Новые id выходят вместе с новыми версиями
   Astra. Демон, отклоняющий неизвестный id, превратил бы каждое
   добавление в день поломки для каждого более старого демона.
2. **Хеш.** `permissions_hash` (§5) вычисляется по этим байтам тремя
   реализациями. Отбрасывание ключа, который читатель не распознал,
   заставило бы двух из них разойтись в том, что было подписано.

Неизвестный id **бездействует** — по умолчанию всё запрещено значит он
ничего не даёт, никогда — и это не происходит молча. Лист согласия
отрисовывает его через собственную метку `permission.unrecognised`, а не
отбрасывает, так что пользователю сообщают, что плагин просит что-то,
чего эта версия Astra не знает. `Permissions::unknown()` существует,
чтобы инструменты могли их перечислить; **`astra-plugin check` сегодня
этого не делает** — она сообщает, что раздел `[permissions]`
присутствует, и на этом останавливается.

(`[capabilities]`, напротив, — `deny_unknown_fields`: это закрытый набор
булевых значений, где опечатка читается ровно как `false`.)

## 2. По умолчанию всё запрещено, и четыре RPC, которым ничего не нужно

**Отсутствующий раздел `[permissions]` не даёт RPC хоста сверх всегда
разрешённого набора.** Отсутствующий раздел — это не «не указано»; это
полный ответ, и ответ — нет.

Всегда разрешённый набор состоит из четырёх, и он записан как таблица
(`HOST_RPC_PERMISSIONS` в `host_service.rs`), против которой два
канарейка-теста сверяют каждый RPC, так что незакрытый новый RPC — это
провал теста, а не тихий пропуск:

| RPC | разрешение |
|---|---|
| `Register` | — |
| `PluginLog` | — |
| `GetPluginSelfConfig` | — |
| `GetDaemonInfo` | — |
| `SubscribeEvents` | `subscribe_events` |
| `SendChatMessage` | `send_chat_message` |
| `FireTrigger` | `fire_trigger` |
| `SetVariable` | `set_variable` |
| `SetThemeContribution` | `set_theme_contribution` |
| `PushToUi` | `push_to_ui` |

`GetDaemonInfo` — единственное добавление к списку из трёх в плане, и это
решение, а не упущение: он возвращает `version`, `state`, `grpc_port` и
`language`, всё это уже было передано вызывающему через
`PluginRegisterResponse`, так что он не раскрывает ничего нового.
Изобретение id разрешения для него поставило бы перед пользователем
чекбокс, который ничего не защищает, а чекбоксы, которые ничего не
защищают, — это то, как пользователи учатся тикать чекбоксы не глядя.

**`client_session_token` выдаётся каждому плагину.** Токен — это
*аутентификация* (кто вызывает), а не *авторизация* (что ему разрешено).
Отказ выдать его плагинам без `client` лишил бы `PluginLog`,
`GetPluginSelfConfig`, `SubscribeEvents` и `FireTrigger` — всегда
разрешённый набор — и сломал бы каждый плагин и оба сайдкара in-tree.
Шлюз `client` принадлежит потолку и конкретным поверхностям, а не токену.

## 3. Объявить — значит попросить; выдача — другой объект

**Ничто в `plugin.toml` не является выдачей.** Блок `[permissions]` — это
*запрос* автора. **Выданный набор** — отдельный объект, который демон
вычисляет по пути происхождения и хранит там, куда плагин не может
дотянуться, — `<base_dir>/registry/records/<id>.json`, соседний с деревом
плагинов, но никогда не его потомок, с MAC по ключу, который держит
демон.

Применение читает выданный набор и никогда манифест — форма вызова в
начале каждого закрытого RPC (иллюстративный отрывок из
`host_service.rs`, не исполняемый пример):

```rust
let (plugin_id, grants) =
    self.require_permission(&request, Permission::FireTrigger, "FireTrigger").await?;
```

Плагин, способный расширить собственные выдачи, редактируя собственный
манифест, имел бы систему разрешений, являющуюся комментарием. Это было
буквально верно до фазы 4: `[capabilities] dom_access = true` — одна
строка в файле внутри собственного каталога плагина — копировалась прямо
на UI-вклад, который отрисовщик уважает, загружая скрипт плагина прямо в
окно Astra.

**Почему запись не в каталоге плагина.** Плагин работает от имени
пользователя, с `current_dir`, установленным в его каталог установки.
Режим 0600 защищает от других пользователей, но не от самого субъекта.
Запись, которую субъект может писать, позволила бы вредоносному плагину
выдать себе `dom_access`, перезаписать TOFU-закрепление, переписать
`artifact_sha256`, чтобы обойти отзыв по ключу дайджеста, и переписать
хеши отдельных файлов, чтобы повторная проверка при старте прошла.

### 3.1 Мост возможностей

`dom_access` и `client` — это одновременно булевы `[capabilities]` и id
разрешений. Каждый плагин, написанный до разделения, говорит, что хочет,
в старом месте — включая `companion`, `doom` и `bad-apple`, ни один из
которых вообще не объявляет раздел `[permissions]`.

Так что бит `[capabilities] dom_access = true` читается как **запрос**,
точно так же, как запись `[permissions]`, и получает точно такой же
ответ из той же таблицы (`declared_permissions()`). Мост намеренно *не*
устроен как «бит возможности выдаёт разрешение»: он кладёт бит туда, где
живёт запрос, так что есть один ответ на «можно ли?», а не два.

Следствие для авторов: **плагин, опубликованный через реестр, обязан
объявить `[permissions] dom_access`**, потому что установка из реестра
выдаёт из своей записи доверия, которая пишется из блока `[permissions]`
`MANIFEST.json` бандла — и именно эту запись отрисовывает лист согласия
и отмечает пользователь.

## 4. Откуда берётся выданный набор

### 4.1 Четыре пути происхождения

`decide_grants()` — эта таблица в виде одной чистой функции.

| путь | выданный набор |
|---|---|
| **Встроенный сайдкар** (`builtin_stt`, `builtin_vox`) | набор, **объявленный в коде**, рядом с `build_manifest()` этого сайдкара. Нет записи доверия, нет чтения с диска — у сайдкара нет записи *по замыслу*, так что путь кода, который бы её искал, был бы путём кода, который может для неё провалиться |
| **Установка из реестра** | запись доверия, записанная при установке: `MANIFEST.permissions` бандла, после проверки согласия, ограниченная потолком уровня |
| **`ImportPluginFile`** (`.astraplugin` не через каталог) | запись доверия на `tier: "local-unverified"` — объявленный набор манифеста, **ограниченный потолком уровня 2** |
| **Сайдлоад** (каталог с исходниками, режим разработчика) | запись доверия на `tier: "sideloaded"` — объявленный набор манифеста, **без потолка** |

Четыре ветви *не* в этой таблице и одинаково нормативны:

| состояние | выдано |
|---|---|
| `Untrusted` — запись ожидалась, но ей нельзя верить | **ничего** |
| `TamperDetected` — файл больше не совпадает с записанным для него дайджестом | **ничего** |
| `Revoked` — покрыт подписанным списком отзыва | **ничего** |
| `Unrecorded` — установлен до появления записей доверия, записи вообще нет | объявленный набор манифеста, **ограниченный потолком уровня 2** |

`Untrusted` всё ещё может быть запущен вручную, и когда это происходит,
он запускается без выдач: «пользователь попросил» — не доказательство
про байты. `Unrecorded` ограничивается потолком, а не отклоняется, потому
что не выдать таким плагинам ничего сломало бы рабочие установки при
обновлении, и пользователю не на что было бы это исправить, а выдать им
их манифест без потолка позволило бы любому из них выдать себе
`dom_access`, отредактировав файл в собственном каталоге. Потолок уровня
2 — это ровно форма «пришёл откуда-то, ничего не доказал».

`Verified`-плагин без записи, которой можно верить, получает **ничего**:
`Verified` *означает* запись, которой можно верить, и ответом на
невозможную комбинацию не является откат к манифесту.

Каждый отказ называет источник (`GrantSource::describe`) — «отказано» без
«и вот источник, которому нечего было об этом сказать» — это тот режим
сбоя, из-за которого систему разрешений откатывают.

### 4.2 Два шлюза, не один

Разрешение соблюдается только когда верны **оба**:

1. **выдача** — ответ на уровне конкретной установки, который создал
   лист согласия и который держит запись доверия;
2. **потолок** — правило на уровне происхождения, которое никакая запись
   не может выкупить.

`require_permission` спрашивает первое для шести RPC хоста, закрытых
разрешением, — `SubscribeEvents`, `SendChatMessage`, `FireTrigger`,
`SetVariable`, `SetThemeContribution`, `PushToUi`. Остальные четыре
(`Register`, `GetPluginSelfConfig`, `PluginLog`, `GetDaemonInfo`) несут
`None` в `HOST_RPC_PERMISSIONS` и разрешены всегда; таблица и обоснование
— в §2.
`ceiling_admits`
спрашивает второе везде, где выдаётся *поверхность*, — `PluginStatusMsg`,
ответ UI-вкладов, ответ активных тем, — так что отрисовщик никогда не
получает значение, которое мог бы уважить. Плагин, отсутствующий в карте
выдач, отклоняется: «ничего о нём не вычислено» — не причина отдавать ему
самую высокорисковую поверхность в системе.

## 5. Потолки уровней

| уровень | источник | потолок |
|---|---|---|
| **1 · Реестр** | верифицирован по алгоритму установки | **всё**, при условии согласия. Нет обхода при провале |
| **2 · Локальный файл** (`ImportPluginFile`) | `.astraplugin`, полученный не через каталог | `send_chat_message`, `set_theme_contribution`, `dom_access` и `client` **отклоняются безусловно, без предупреждения** |
| **3 · Сайдлоад** | каталог с исходниками, на который пользователь указал через диалог выбора файла, режим разработчика включён | **нет** — и он **никогда не запускается автоматически**: режим разработчика нужен в момент загрузки, и перезапуск оставляет его остановленным, пока пользователь не запустит его снова |

Уровень сайдлоада показывается пользователю как `provenance.tier.sideloaded`
(«загружено из папки») в панели происхождения. План также просит
постоянный, неубираемый бейдж «РАЗРАБОТЧИК — неверифицированный код из
локального каталога» на карточке и на рамке окна для `dom_access`;
**этого бейджа сегодня нет в интерфейсе**, и этот документ этого не
утверждает.

**Продвижение с уровня 2 не реализовано.** План описывает продвижение
импортированного файла до уровня 1, когда его дайджест появляется в
свежем индексе, а нижние границы версий соблюдены; сегодня
`import_plugin_file` не передаёт верифицированный релиз в путь установки,
так что импортированный бандл **всегда** `local-unverified`, что бы
индекс ни говорил о его дайджесте. Не говорите автору, что публикация
задним числом поднимет потолок файла, который он кому-то отправил по
почте.

Список отказа уровня 2 — это `TIER2_REFUSED_PERMISSIONS` — намеренно
**не** тот же список, что `HIGH_RISK_PERMISSIONS`: `push_to_ui` стоит
чекбокса, но не стоит отклонения файла, который пользователь выбрал
импортировать. Эти четыре процитированы из §5.5, а не выведены.

**Уровень 3 — это не уровень 2 с бейджем покрасивее.** Разделение — по
*намерению*, а не по статусу верификации. Пользователь, указавший через
диалог выбора файла на каталог на собственном диске, дал более сильный
сигнал, чем неверифицированный файл, пришедший откуда-то ещё, — а
`companion`, `doom` и `bad-apple`, собственные флагманские примеры этого
проекта, все нуждаются в DOM-пути, который отклоняет уровень 2.
Ограничение уровня 3 потолком сделало бы `astra-plugin dev` невозможным.

Неизвестные id отбрасываются любым потолком (`capped()` фильтрует по
`Permission::from_id(id).is_some_and(keep)`): потолок, пропускающий id,
которые он не может классифицировать, был бы потолком с дырой в форме
следующего релиза.

**Правило дизайна, соблюдаемое везде:** *единственное, что может купить
обход пользователя, — это право запускать код из источника, который
Astra не проверила. Оно никогда не может купить разрешение, которое
верифицированному плагину пришлось бы попросить.*

## 6. Согласие

Лист согласия отрисовывается **до какой-либо загрузки**, из `permissions`
записи каталога — которую реестр скопировал из `MANIFEST.json` бандла при
приёме.

* Каждый id отрисовывается через **собственную таблицу локализованных
  меток Astra**. `reason` автора подчинён: в кавычках, простым текстом, ≤
  140 символов, всегда с префиксом *«The author says:»*. Это никогда не
  сама метка — формулировки фиксируются в поставке Astra и не должны быть
  настраиваемы через листинг.
* Каждое высокорисковое разрешение получает **свой чекбокс**; `dom_access`
  получает второй экран.
* Ответ едет в установку как **потолок, не запрос**
  (`InstallOptions::consent`): установка отклоняется с
  `PERMISSIONS_NOT_CONSENTED`, если *бандл* просит что-то, чего лист не
  показывал. Два списка приходят из разных мест — лист отрисовывает
  запись каталога, запись доверия выдаёт из собственного манифеста
  бандла — и ничто другое не заставляет их совпадать. Заявка, ничего не
  объявляющая, при поставке бандла, просящего `dom_access`, — это случай
  «злонамеренного реестра», нацеленный прямо на экран согласия.
* `consent: None` — унарная установка, импорт, тест, усыновление —
  сохраняет поведение до-согласия: выдать объявленный набор бандла,
  ограниченный уровнем.

**Обновления.** Версия, просящая разрешение, которого не было выдано
установленной версии, отклоняется с `PERMISSIONS_WIDENED` и становится
запросом на ревью; явное одобрение пользователя — это то, что превращает
его в установку. Сравнение **по имени разрешения, никогда по всему
объекту запроса**: автор, улучшивший формулировку `reason`, ничего не
расширил, и шлюз обновления, трактующий это как расширение, приучил бы
пользователей проходить сквозь единственный диалог, который важен.

**Отзыв вступает в силу немедленно.** При любом изменении
`granted_permissions`, при отказе в согласии и при отзыве демон сбрасывает
подписку на стороне сервера и обесценивает токен сессии, так что живой
поток событий не может пережить сужение. Плагину сообщают, что из этого
произошло, через трейлер `x-astra-teardown-reason` (`grants_changed`,
`consent_declined`, `revoked`, `trust_lost`, `disabled`, `uninstalled`,
`re_registered`) — стабильный токен, так что SDK никогда не приходится
разбирать английский текст, чтобы понять, бессмысленен ли повтор.

### 6.1 Как написать хороший `reason`

Он показывается пользователю, который принимает решение. Он **ОБЯЗАН**
быть ≤ 140 символов и **СЛЕДУЕТ**:

* называть **фичу, которую узнаёт пользователь**, а не API — *«Запускает
  триггер on_dice_roll, который вы настроили»*, а не *«вызывает
  FireTrigger»*;
* говорить **когда**, если не всегда — *«только пока идёт запись»*;
* избегать повторения собственной метки разрешения; Astra уже её
  отрисовала;
* избегать срочности, угроз или инструкций пользователю. Генератор
  отклоняет текст, содержащий bidi-переопределения или соединители
  нулевой ширины везде, где он отображается дословно, и лист согласия —
  последнее место для исключения.

Разрешение без правдоподобного reason — это разрешение, которое нужно
удалить из манифеста — автоматически это никто не проверяет, и
единственный заслон — рецензент, читающий заявку.

## 7. `permissions_hash`

```
permissions_hash = "sha256:" ‖ lowercase_hex( SHA256( JCS(permissions) ) )
```

* `JCS` — это каноничный JSON по RFC 8785 — ключи отсортированы по
  единице кода UTF-16, компактно. См.
  [`registry-index.md` §3](registry-index.md#3-канонизация-профиль-jcs)
  насчёт профиля, который реализуют оба репозитория.
* **`null` и `{}` — одно и то же значение** и хешируются одинаково, так
  что производитель, опускающий член, и тот, что пишет пустой объект,
  согласны:
  `sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`.
* **Пустые члены опускаются, а не выдаются пустыми.** `set_variable = {}`
  — это `{}`, никогда не `{"reason":""}`. Два каноничных написания одного
  объявления — это ровно то расхождение, для предотвращения которого
  существует этот хеш.
* Префикс `sha256:` — часть значения, потому что он пересекает границу
  репозитория.

Три реализации вычисляют его, и все три сравниваются: упаковщик
`astra-plugin` пишет его в `MANIFEST.json`; бот реестра пересчитывает его
при приёме и отказывается включить в каталог при расхождении
(`E_PERMISSIONS_HASH_MISMATCH`); демон пересчитывает его прежде, чем
поверить манифесту, и блокирует установку
(`PERMISSIONS_HASH_MISMATCH`). Эталонные векторы: `ok-permissions`
(корректная непустая карта) и `permissions-hash-mismatch` — см.
[`bundle-v2.md` §10](bundle-v2.md#10-permissions-и-permissions_hash) и
расхождение F5, которое касается только читателя CLI.

Хеш также записан в запись доверия и перепроверяется при обнаружении,
так что `plugin.toml`, отредактированный на месте после установки,
обнаруживается, а не соблюдается.

## 8. Чем разрешения не являются

`[permissions]` отвечает на вопрос *что демон сделает для плагина*. Она
не отвечает на вопрос *что процесс может сделать с машиной*.

Плагин — это нативный процесс, запущенный демоном, работающий от имени
пользователя с его полными правами. Он может читать файлы пользователя,
открывать сокеты и — сегодня — читать собственный токен демона с диска.
**Песочницы нет.** Изоляция (Landlock/seccomp, AppContainer или токен
низкой целостности на Windows, rlimits) обозначена как будущая работа и
явно не входит в этот релиз.

Два следствия, которые этот документ требует соблюдать от каждого
потребителя:

* **Интерфейс Astra никогда не должен намекать на песочницу.** Блок «не
  доказывает» панели происхождения и однострочник листа согласия
  существуют именно по этой причине.
* **Отказ в разрешении — реальная граница только для собственных
  полномочий демона** — автоматизации, ход чата, тема, окно. Для всего
  остального это растяжка, а не тюрьма.

Быть честным здесь — не оговорка, прикрученная в конце. Модель
разрешений, описываемая как песочница, — это модель разрешений, чьи
пользователи принимают худшие решения, чем приняли бы вообще без модели.

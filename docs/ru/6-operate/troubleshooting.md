# Диагностика

> Перевод. Источник истины — [docs/en](../../en/6-operate/troubleshooting.md); при расхождении верна английская версия.

Привязана к строкам, которые реально печатают CLI и демон. Если перед вами
ошибка, ищите на этой странице её фрагмент.

## Начните отсюда

<!-- doctest: cli -->
```bash
astra-plugin doctor
```

Пятнадцать проверок, каждая сформулирована как вопрос, на который отвечает.
Она знает, какой CLI вы используете, какой каталог конфигурации она
разрешила, доступен ли демон, какие у вас тулчейны, разбирается ли ваш
манифест, существует ли точка входа, покрывают ли ваши разрешения ваши
возможности, правильный ли у вас блок `[platform]`, и закреплён ли ваш
workflow релиза. Каждый сбой несёт строку `fix:`. В проекте, который вы ещё
не собирали, она выходит с ненулевым кодом на одном из них — «Will the
daemon find something to start? … does not exist» — и это правильно: бинарник
ещё никто не произвёл.

## Проект не может разрешить свой SDK

**`error: failed to select a version for the requirement astra-plugin-sdk = "^0.6"`**
**`ERROR: No matching distribution found for astra-plugin-sdk<0.6,>=0.5`**
**`error: No version matching "^0.5.0" found for specifier "astra-plugin-sdk" (but package exists)`**

Три языка, одна форма ошибки — и отсутствие SDK больше не является её
причиной. `astra-plugin new` закрепляет `astra-plugin-sdk` `0.6` для Rust,
`>=0.5,<0.6` для Python и `^0.5.0` для TypeScript, а публичные реестры
несут crates.io **0.6.0**, PyPI **0.5.0** и npm **0.5.0**. Каждое из этих
закреплений разрешается в свежем проекте без какой-либо настройки, так что
если у вас не разрешается, причина — между вашей машиной и реестром:

- **Устаревший индекс, lock-файл или зеркало, которое не синхронизировалось.**
  Резолвер отвечает из кэшированного вида реестра, снятого до релиза, или из
  корпоративного прокси, который делает то же самое. `cargo update -p
  astra-plugin-sdk`; `pip install --upgrade --no-cache-dir -r requirements.txt`;
  для npm — удалить `node_modules` и lock-файл и установить заново.
  `cargo --offline` и `npm --offline` дают эту ошибку по определению.
- **Кто-то ослабил границу.** Пин, отредактированный до `0.5` (Rust) или `0.4`
  (Python, TypeScript), просит то, чего ни один реестр под таким ограничением
  не предлагает. Верните пин из шаблона, а не расширяйте его дальше: 0.6 —
  первый релиз Rust, чей `HostClient` прикрепляет `x-session-token`, так что
  более старый SDK меняет эту ошибку на `unauthenticated` при каждом вызове
  хоста — следующий раздел.

Ни `doctor`, ни `check` об этом не упомянут, потому что оба читают
`plugin.toml`, а закрепление живёт в файле сборки самого языка.

## Плагин не запускается

**`Could not read /…/astra/daemon.token. Astra does not look like it is running — start the app first.`**
Ровно то, что там написано. `dev`, `logs` и установка требуют запущенной
Astra; `new`, `build`, `check`, `test`, `sign` и `publish` — нет. Если Astra
*запущена*, значит она разрешила другой каталог конфигурации, чем CLI, —
сравните путь, который печатает `doctor`, с тем, что показывает Astra в
своих настройках.

**Демон убрал процесс при старте.** Бюджет — `plugin_start_timeout_secs` =
**20 с** до первой строки вывода. Python-плагин, импортирующий большой
ML-стек на уровне модуля, может в него не уложиться; импортируйте лениво,
внутри того хука, которому это нужно. `astra-plugin test` это измеряет и
печатает число:

<!-- doctest: output from="astra-plugin test . --no-build" unrun="starts a real plugin process and runs the conformance suite against it; needs a built plugin" -->
```
  [ok  ] the plugin says something before the daemon gives up: first line on stdout after 792.4µs
         (the daemon waits 20s, spec/limits.yaml plugin_start_timeout_secs)
```

**Плагин запускается и сразу падает.** Сначала проверьте `astra-plugin logs
-f`; если там вообще ничего нет, процесс падает до того, как SDK
установит своё логирование. Запустите бинарник вручную — `astra-plugin dev
--standalone` делает это и говорит, чего так сделать нельзя.

**Ошибки `HealthCheck` помечают плагин мёртвым.** Она выполняется каждые
15 с и не проходит через опциональный хелпер демона для необязательных
хуков: *любая* ошибка, включая `UNIMPLEMENTED`, значит «мёртв». Если вы
переопределили `health_check`, убедитесь, что она не может бросить
исключение.

## Вызов хоста возвращается с `permission_denied`

Сообщение называет разрешение и откуда взялся выданный набор. Три причины,
по убыванию вероятности:

1. **Вы его не объявили.** `[permissions]` по умолчанию запрещает всё.
   Объявление `[capabilities] event_handlers = true` не даёт `SubscribeEvents`;
   это делает `[permissions] subscribe_events`.
2. **Пользователь его не выдал**, или путь установки его ограничил. У
   [локально импортированного файла](../5-publish/local-install.md)
   `send_chat_message`, `set_theme_contribution`, `dom_access` и `client`
   отклоняются безусловно.
3. **Вы вышли из аккаунта или приложение заблокировано.** Astra отклоняет
   RPC плагинов в обоих состояниях, и CLI об этом говорит: *«Astra refuses
   plugin RPCs while signed out or locked — sign in and unlock the app,
   then try again.»*

`astra-plugin doctor` отвечает на пункт 1, ничего не запуская:

<!-- doctest: output from="astra-plugin doctor ." unrun="reports this machine's toolchains, daemon and config paths, so its output differs on every machine" -->
```
  [ok  ] Why is a host call coming back `permission_denied`?
         [permissions] grants: none. Every declared capability has the host rpc it needs.
```

## Вызов хоста возвращается с `unauthenticated`

Каждый вызов `PluginHostService`, кроме `Register`, обязан нести токен
сессии в `x-session-token`. Все три SDK его прикрепляют — **начиная с 0.6 в
Rust, 0.5 в Python и TypeScript**. Против более старого SDK каждый вызов
хоста проваливается именно так, и поэтому граница зависимости в заготовке
не опускается ниже.

`astra-plugin test` проверяет это от начала до конца:

<!-- doctest: output from="astra-plugin test . --no-build" unrun="starts a real plugin process and runs the conformance suite against it; needs a built plugin" -->
```
  [ok  ] every host call carried the session token: no host call was refused for want of `x-session-token`
```

## Сайдлоадинг отклоняется

**`Sideloading is disabled.`** `safety.allow_unsigned_plugins` выключен.
Прочтите, [чего стоит его включение](../5-publish/sideload.md), прежде чем
это делать.

**`Refusing sideload marker in …: this daemon never authorised a sideload of …`**
Кто-то вручную подложил `sideload.json`. Это не работает с тех пор, как
демон начал вести собственную запись того, что он авторизовал. Используйте
`astra-plugin dev`.

## Установка отклоняется

Каждый провал верификации на пути через каталог — это **жёсткий блок без
обхода**, и каждый называет, какая из двух вещей произошла.

| Что вы видите | Что это значит |
|---|---|
| Скачанный файл не совпадает с тем, что подписал реестр | `DIGEST_MISMATCH` — загрузка отброшена. Сообщите об этом |
| Astra не смогла верифицировать подпись каталога плагинов | `SIGNATURE_INVALID` — магазин отключается, а не откатывается к неверифицированным данным |
| Это обновление пришло из другого репозитория, чем тот, откуда вы устанавливали | `IDENTITY_CHANGED` — обхода нет никогда. Только удаление снимает закрепление |
| Плагин был отозван | `REVOKED` — с советом и удалением в один клик. Файлы никогда не удаляются молча |
| Этот бандл для другой платформы | `PLATFORM_UNSUPPORTED` |
| Этому плагину нужна более новая Astra | `PROTOCOL_UNSUPPORTED` |
| Сеть, или неверны часы | Можно повторить, и сформулировано именно так. Это никогда не должно выглядеть как провал верификации |

**`nothing here vouches for these bytes`** для локального файла: установите
его со страницы плагинов вместо этого, или прочтите про
[локальную установку](../5-publish/local-install.md), чего стоит импорт.

Сегодня цепочка доверия заякорена **на одно звено меньше, чем нужно**:
корневые ключи существуют, и подписанный корнём `trust.json`, делегирующий
ключ подписи индекса, тоже теперь существует, но `registry/v1/index.json` и
`revocations.json` всё ещё несут `"signatures": []`. Без подписи на
каталоге делегированному ключу нечего проверять, так что каталог
классифицируется как неподписанный, и отзыв не применяется. См.
[`spec/registry-index.md` §0.1](../spec/registry-index.md).

## Вызов инструмента проваливается так, что модель не может это исправить

Используйте правильный код; именно его читает модель.

| Код | Используйте, когда |
|---|---|
| `BAD_ARGUMENTS` | Повтор с другими аргументами мог бы сработать |
| `NOT_CONFIGURED` | Отсутствует настройка — **и задайте `config_field`**, именно это превращает ошибку в ссылку на конкретное поле |
| `UNAUTHORIZED` | Значение есть, но было отклонено. Отличается от `NOT_CONFIGURED` |
| `RATE_LIMITED` | С `retry_after_ms`, когда его назвал вышестоящий сервис |
| `UNAVAILABLE` / `TIMEOUT` | Временно. Более поздний идентичный вызов может сработать |
| `INTERNAL` | Баг. Модель ничего с этим не сделает |

`UNIMPLEMENTED` — это **не** ошибка: она означает «этого хука нет», и демон
читает её именно так. Вернуть её, потому что упал ваш TTS, заставит демона
поверить, что у вас вообще нет TTS. Полная таксономия:
[`reference/errors.md`](../reference/errors.md).

## `astra-plugin check` жалуется

**`config.schema is not valid JSON`** или **`should have "type": "object" at
root`** — форма настроек генерируется из этой схемы.

**Неизвестный ключ в `[capabilities]` роняет весь манифест.** Этот раздел —
единственное место, где неизвестные ключи отклоняются, потому что каждый
ключ — это булев признак согласия, и опечатка иначе читалась бы ровно как
`false`. `ui_panels` — классика: правильно `ui_contributions`, и три
примера из поставки месяцами не объявляли вообще ничего именно из-за этого.

**Неизвестный id в `[permissions]` сохраняется, и о нём предупреждают**, а
не отклоняют — новые id выходят вместе с новыми версиями Astra, а блок
разрешений хешируется побайтово тремя реализациями, так что отбрасывание
ключа заставило бы их разойтись в том, что было подписано.

`astra-plugin check --fix` применяет то, что может доказать, и сообщает об
остальном.

## CLI не печатает ничего полезного

`RUST_LOG` теперь работает — она документировалась с 0.1 и была
бездейственной, пока не установили подписчика:

<!-- doctest: cli -->
```bash
RUST_LOG=astra_plugin=debug astra-plugin check
RUST_LOG=debug astra-plugin build
```

Трассировка идёт в **stderr**, так что `--json` на stdout остаётся чистым
единым документом.

## Коды выхода

| | |
|---|---|
| `0` | успех |
| `1` | плагин или бандл неправильный |
| `2` | CLI не смогла выполнить проверку — отсутствующий файл, отсутствующий тулчейн |

Это разделение — несущее: workflow релиза, который относится к «бандл
плохой» и «я не смог посмотреть» одинаково, поставит один из них.

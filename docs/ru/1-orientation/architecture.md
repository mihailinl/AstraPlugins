# Архитектура

Как запускается процесс плагина, как он доказывает, кто он такой, и какой из
двух gRPC-сервисов какие вызовы несёт.

## Модель процессов

<!-- doctest: illustrative reason="ASCII-схема двух сервисов, а не код" -->
```
   ┌──────────────────────────┐                  ┌──────────────────────────┐
   │      демон Astra         │                  │      ваш плагин          │
   │                          │   запускает с    │   (отдельный процесс      │
   │  менеджер плагинов ──────┼──── argv ───────▶│    ОС, ваша учётная      │
   │                          │                  │    запись)               │
   │                          │                  │                          │
   │  PluginHostService       │◀── плагин зовёт ─┤  HostClient              │
   │  (обслуживает демон)     │   x-session-token│                          │
   │                          │                  │                          │
   │  клиент возможностей ────┼── демон зовёт ──▶│  PluginCapabilityService │
   │                          │   x-plugin-token │  (обслуживает плагин)    │
   └──────────────────────────┘                  └──────────────────────────┘
            оба конца — gRPC поверх loopback TCP
```

Демон запускает процесс с четырьмя аргументами. Это точная командная строка,
скопированная из реального запуска `astra-plugin test`:

<!-- doctest: output from="astra-plugin test . --no-build, в сгенерированном плагине" -->
```
target/release/dice_roller --daemon-addr=127.0.0.1:46495 --plugin-id=dice-roller \
  --auth-token=mock-daemon-spawn-token --capabilities=tools
```

SDK разбирает их за вас. Самый интересный — `--auth-token`: это секрет, который
демон выпустил для этого запуска, и он используется в **обоих** направлениях.

## Порядок запуска

SDK выполняет фиксированную последовательность
(`astra-plugin-sdk/src/runner.rs`):

<!-- doctest: illustrative reason="порядок запуска прозой, цитата из runner.rs" -->
```
bind → register → build ctx → on_config → on_language_changed → on_start → serve
```

- **bind до register**, потому что порт сообщается демону в `Register`, и он
  может позвонить обратно немедленно. Слушатель уже поднят, поэтому такие
  вызовы встают в очередь accept, а не отвергаются.
- **`on_config` до `on_start`**, потому что плагину, запускающему фоновый цикл,
  сначала нужны его настройки.
- **`on_start` до `serve`**, и `Err` оттуда **прерывает запуск**: плагин,
  который не может делать свою работу, не должен быть плагином, который демон
  считает здоровым.

Это ограничено двумя числами, объявленными один раз в
[`spec/limits.yaml`](../../../spec/limits.yaml) и сгенерированными в каждый SDK:

| Лимит | Значение | Что происходит, если не уложиться |
|---|---|---|
| `plugin_start_timeout_secs` | 20 | Демон считает запуск неудачным и убивает процесс |
| `plugin_stop_grace_secs` | 5 | После `Shutdown` группа процессов убивается |

## Рукопожатие

1. Демон запускает процесс с `--auth-token=<токен запуска>`.
2. Плагин поднимает gRPC-сервер на выданном ОС порту loopback.
3. Плагин вызывает `PluginHostService.Register`, предъявляя токен запуска, свой
   порт, версию протокола и список возможностей.
4. Демон отвечает **сессионным токеном**.
5. Каждый следующий вызов плагин → демон несёт этот токен в метаданных
   `x-session-token`. `Register` — единственный путь-исключение
   (`astra-plugin-sdk/src/auth.rs`); всё прочее без токена возвращает
   `unauthenticated`.

Регистрация в реальном прогоне против mock-демона, который поднимает
`astra-plugin test`:

<!-- doctest: output from="astra-plugin test . --no-build" -->
```
INFO astra_plugin_sdk::runner: Starting plugin 'dice-roller', connecting to daemon at 127.0.0.1:46495
INFO astra_plugin_sdk::runner: Plugin gRPC server listening on port 41627
INFO astra_plugin_sdk::runner: Registering with capabilities: ["tools"]
INFO astra_plugin_sdk::runner: Registered successfully. Daemon version: mock, protocol: 1 (accepts 0+)
```

### Обратное направление, и что в нём не доделано

Направление демон → плагин использует *тот же* токен запуска, отправляемый
плагину в заголовке `x-plugin-token`. Ваш сервер возможностей его проверяет.

Сегодня SDK по умолчанию работает в режиме `CapabilityAuth::Warn`: **неверный**
токен отвергается, а **отсутствующий** принимается с предупреждением, потому
что демоны без этого заголовка ещё встречаются. Это реальная, до сих пор
открытая дыра, и документация не будет делать вид, что её нет: пока демон не
выпустит свою половину, любой процесс от вашего имени может найти loopback-порт
плагина и вызвать у него `CallTool`, `OnConfigChanged` или `Shutdown`.

`ASTRA_PLUGIN_CAPABILITY_AUTH=require` включает проверку заранее; по умолчанию
она включится, когда демон начнёт слать заголовок (`astra-plugin-sdk/src/auth.rs`).

## Два сервиса

| | `PluginCapabilityService` | `PluginHostService` |
|---|---|---|
| Обслуживает | ваш плагин | демон |
| Вызывает | демон | ваш плагин |
| Управляется | `[capabilities]` | `[permissions]` |
| Хуков | 25 | 10 |

`PluginService` — третий сервис в proto — демон обслуживает для интерфейса
Astra. Ни один плагин его не трогает; `astra-plugin dev` и `astra-plugin logs`
обращаются к нему как локальный клиент.

Каждый хук с его возможностью, разрешением, обязательностью и строкой демона,
которая его вызывает: [таблица паритета](../../en/reference/parity.md).

## Здоровье, завершение и перезапуски

- `HealthCheck` выполняется каждые 15 с и **не** считается необязательным:
  любая ошибка, включая `UNIMPLEMENTED`, помечает плагин мёртвым.
- На `Shutdown` вы отвечаете и выходите. На это даётся 5 секунд.
- Паника внутри обработчика перехватывается и возвращается ошибкой, а не
  разматывается через gRPC-сервер (`astra-plugin-sdk/src/panics.rs`). Паника
  по-прежнему баг — просто не авария.

## Конфигурация

Настройки плагина — это JSON, который хранит демон и который правят в интерфейсе
Astra по JSON Schema из вашей секции `[config]`. Демон доставляет их через
`OnConfigChanged`, и плагин может запросить их сам через `GetPluginSelfConfig` —
один из четырёх вызовов, не требующих разрешения.

Первая доставка свежеустановленному плагину — это `{}`, поэтому типы настроек в
SDK задают значение по умолчанию для каждого поля. См.
[поля настроек](../../en/3-reference/config-fields.md).

Файл настроек — `<каталог конфигурации Astra>/plugins/<id>/config.json`
(пути по ОС — в [платформах](platforms.md)). Он **переживает обновление**:
обновление — это стоп, установка, старт, а установка раньше делала
`remove_dir_all` по каталогу, где лежали настройки пользователя. Теперь демон
сохраняет файл и проверяет это тестом (`config_survives_update`,
`astra-daemon/src/plugins/manager.rs`), а копия, положенная в новый архив, не
может его перезаписать. Удаление плагина он **не** переживает:
`uninstall_plugin` заканчивается на `remove_dir_all`. Всё, что должно пережить
удаление, храните там, где владелец вы.

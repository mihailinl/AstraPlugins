# Архитектура

> Перевод. Источник истины — [docs/en](../../en/1-orientation/architecture.md); при расхождении верна английская версия.

Как запускается процесс плагина, как он доказывает, кто он такой, и какой из
двух gRPC-сервисов несёт какой вызов.

## Модель процессов

<!-- doctest: illustrative reason="an ASCII diagram of the two services, not code" -->
```
   ┌──────────────────────────┐                  ┌──────────────────────────┐
   │      Astra daemon        │                  │     your plugin          │
   │                          │   spawns with    │     (a separate OS       │
   │  plugin manager ─────────┼──── argv ───────▶│      process, your       │
   │                          │                  │      user account)       │
   │                          │                  │                          │
   │  PluginHostService       │◀── plugin calls ─┤  HostClient              │
   │  (the daemon serves)     │   x-session-token│                          │
   │                          │                  │                          │
   │  capability client ──────┼── daemon calls ─▶│  PluginCapabilityService │
   │                          │   x-plugin-token │  (your plugin serves)    │
   └──────────────────────────┘                  └──────────────────────────┘
             both ends are gRPC over loopback TCP
```

Демон запускает процесс с четырьмя аргументами. Это точная командная строка,
скопированная из реального запуска `astra-plugin test`:

<!-- doctest: output from="astra-plugin test . --no-build, in a scaffolded plugin" -->
```
target/release/dice_roller --daemon-addr=127.0.0.1:46495 --plugin-id=dice-roller \
  --auth-token=mock-daemon-spawn-token --capabilities=tools
```

SDK разбирает их за вас. Интересен здесь `--auth-token`: это секрет, который
демон выпустил для этого запуска, и используется он в **обоих** направлениях.

## Порядок запуска

SDK выполняет фиксированную последовательность (`astra-plugin-sdk/src/runner.rs`):

<!-- doctest: illustrative reason="the startup order as prose, quoted from runner.rs" -->
```
bind → register → build ctx → on_config → on_language_changed → on_start → serve
```

- **bind перед register**, потому что порт сообщается демону во время
  `Register`, и он может тут же перезвонить. Слушатель уже поднят, поэтому
  такие вызовы становятся в очередь приёма, а не отклоняются.
- **`on_config` перед `on_start`**, потому что плагину, запускающему фоновый
  цикл, сначала нужны его настройки.
- **`on_start` перед `serve`**, и `Err` из него прерывает запуск: плагин,
  который не может выполнять свою работу, не должен быть тем, что демон
  считает исправным.

Две цифры ограничивают это, каждая объявлена один раз в
[`spec/limits.yaml`](../../../spec/limits.yaml) и сгенерирована в каждый SDK:

| Лимит | Значение | Что происходит, если не уложиться |
|---|---|---|
| `plugin_start_timeout_secs` | 20 | Демон объявляет запуск неудачным и убирает процесс |
| `plugin_stop_grace_secs` | 5 | После `Shutdown` группа процессов убивается |

## Рукопожатие

1. Демон запускает процесс с `--auth-token=<токен запуска>`.
2. Плагин привязывает gRPC-сервер к назначенному ОС loopback-порту.
3. Плагин вызывает `PluginHostService.Register`, предъявляя токен запуска,
   свой порт, версию протокола и список возможностей.
4. Демон отвечает **токеном сессии**.
5. Каждый последующий вызов плагин → демон несёт этот токен сессии в
   метаданном заголовке `x-session-token`. `Register` — единственный
   освобождённый от этого путь (`astra-plugin-sdk/src/auth.rs`); что угодно
   другое без него возвращает `unauthenticated`.

Регистрация в реальном запуске против мок-демона, который поднимает
`astra-plugin test`:

<!-- doctest: output from="astra-plugin test . --no-build" -->
```
INFO astra_plugin_sdk::runner: Starting plugin 'dice-roller', connecting to daemon at 127.0.0.1:46495
INFO astra_plugin_sdk::runner: Plugin gRPC server listening on port 41627
INFO astra_plugin_sdk::runner: Registering with capabilities: ["tools"]
INFO astra_plugin_sdk::runner: Registered successfully. Daemon version: mock, protocol: 1 (accepts 0+)
```

### Обратное направление

Направление демон → плагин использует **тот же** токен запуска, отправляемый
плагину обратно в заголовке `x-plugin-token` при каждом вызове. Ваш сервер
возможностей проверяет его, и SDK делает это за вас.

**Вы это не настраиваете.** Демон устанавливает
`ASTRA_PLUGIN_CAPABILITY_AUTH=require` в окружении вашего плагина, что говорит
SDK отклонять любой вызов возможности без этого токена. Это демон объявляет о
своей собственной половине, а не кто-то сверяет номера версий: демон,
достаточно старый, чтобы не отправлять заголовок, не устанавливает и
переменную, и SDK остаётся в режиме `CapabilityAuth::Warn` —
**неверный** токен отклоняется, **отсутствующий** принимается с одним
предупреждением, — так что ваш плагин там продолжает работать.

Это важно, потому что loopback — не граница. Ваш сервер возможностей слушает
на `127.0.0.1` с назначенным ОС портом, и его может найти любой процесс,
работающий от вашего пользователя. Без заголовка достаточно было его найти,
чтобы вызвать `CallTool`, `OnConfigChanged` — перенаправив базовый URL вашего
API на чужой хост, после чего ваш плагин отправит туда свои настоящие
учётные данные — или `Shutdown`.

`astra-plugin test` устанавливает ту же переменную и предъявляет тот же
токен, так что то, что вы тестируете локально, — это то, что выполняется на
машине пользователя.

## Два сервиса

| | `PluginCapabilityService` | `PluginHostService` |
|---|---|---|
| Обслуживается | вашим плагином | демоном |
| Вызывается | демоном | вашим плагином |
| Регулируется | `[capabilities]` | `[permissions]` |
| Хуков | 25 | 10 |

`PluginService` — третий сервис в proto — обслуживается демоном для интерфейса
Astra. Плагин его никогда не вызывает; `astra-plugin dev` и `astra-plugin
logs` делают это как локальный клиент.

Каждый хук, с его возможностью, разрешением, тем, обязателен ли он, и строкой
исходника демона, которая его вызывает: [таблица паритета](../reference/parity.md).

## Здоровье, завершение и перезапуски

- `HealthCheck` выполняется каждые 15 с и **не** считается опциональным: любая
  ошибка из него, включая `UNIMPLEMENTED`, помечает плагин как мёртвый.
- На `Shutdown` отвечают, а затем выходят. Отсрочка — 5 с.
- Паника внутри обработчика перехватывается и возвращается как ошибка, а не
  раскручивается через gRPC-сервер (`astra-plugin-sdk/src/panics.rs`). Паника
  всё равно остаётся багом; просто это не сбой сервиса.

## Конфигурация

Настройки плагина — это JSON, который хранит демон и который редактируется в
интерфейсе настроек Astra на основе JSON Schema из вашего раздела `[config]`.
Демон доставляет их через `OnConfigChanged`, а плагин может также запросить их
через `GetPluginSelfConfig` — один из четырёх вызовов, не требующих
разрешения.

Первая полезная нагрузка при свежей установке — `{}`, поэтому типы
конфигурации SDK задают значение по умолчанию для каждого поля. См.
[поля настроек](../3-reference/config-fields.md).

Файл настроек — `<каталог конфигурации astra>/plugins/<id>/config.json`
(в [платформах](platforms.md) — точный каталог по каждой ОС). Он
**переживает обновление** — обновление это остановка, установка, запуск, и
раньше установка делала `remove_dir_all` над каталогом, где жили настройки
пользователя; теперь демон сохраняет файл и проверяет это тестом
(`config_survives_update`, `astra-daemon/src/plugins/manager.rs`), и копия,
упакованная в новый архив, не может его перезаписать. Он **не** переживает
удаление: `uninstall_plugin` завершается `remove_dir_all`. Всё, что должно
пережить удаление, должно храниться там, чем владеете вы.

# 安装本地 `.astraplugin` 文件

**这是进阶用法，而且会让你损失四种权限。** 本页描述的是导入一个通过
带外方式送达的包 —— 同事发给你的、你自己构建的、还没上架的一次发布。
这不是插件安装的标准方式；[那是商店的方式](get-listed.md)，在那里
构件(artifact)以摘要固定，验证失败是硬性拦截。

> **把这个文件交给别人，并不是在发布你的插件。** 你构建并发出去的包
> 没有构建证明，也没有注册表记录，所以它只会在你发送到的那一台机器上
> 以较低的层级安装，触及不到任何其他人。发布指的是一次由 CI 构建并
> 出具证明的带标签发布，加上一次上架申请 —— [完整流程一页讲完](../publishing.md)。

## 它是什么

`PluginService.ImportPluginFile` 接受的是一个 **`.astraplugin` 文件的
路径** —— 不是字节内容，也不是一个目录。当你在 Astra 的 UI 中选择一个
文件时，就是它在被调用。

这个包是一个 ZIP 文件，`MANIFEST.json` 是它第一个、未压缩存储的条目。
守护进程会重新推导每一个摘要值，检查文件列表在两个方向上是否都是
穷尽的，任何不匹配的东西都会被拒绝。`astra-plugin verify` 在本地运行
的是同样的检查，你应该在导入别人发给你的文件之前先运行它（如果还没有
CLI，先去[安装 CLI](../install-cli.md)）：

<!-- doctest: cli -->
```bash
astra-plugin verify some-plugin-0.3.0-linux-x64.astraplugin
```

## 上限：四种权限被直接拒绝

一个被导入的文件没有目录记录，所以没有任何东西对它的字节内容进行过
反签名，也没有任何东西把它的作者固定下来。它会以**第 2 层级**安装，
这个层级的上限不是一个警告 —— 这些权限会被**直接丢弃**：

| 无论清单里怎么申请都会被拒绝 | 原因 |
|---|---|
| `send_chat_message` | 像用户亲口说了一样，驱动一次 AI 对话轮次 |
| `set_theme_contribution` | 重新设置整个应用的样式 |
| `dom_access` | 在 Astra 窗口内运行插件的代码 |
| `client` | 成为一个拥有自己会话的聊天前端 |

`fire_trigger`、`subscribe_events`、`set_variable` 和 `push_to_ui`
能够越过这个上限而存活 —— 它们属于权限词汇表中**低风险**的那一端，
这也正是为什么放行它们不需要一次上架来为它们背书。这四个当中，只有
`push_to_ui` 有属于自己的同意勾选框。

这两份清单是刻意区分开来的，值得把两者的区别说清楚：

| 清单 | 成员 | 决定什么 |
|---|---|---|
| `HIGH_RISK_PERMISSIONS` | `send_chat_message`、`push_to_ui`、`set_theme_contribution`、`dom_access`、`client` | 每一项都会得到**它自己的同意勾选框**，无论走哪条安装路径 |
| `TIER2_REFUSED_PERMISSIONS` | `send_chat_message`、`set_theme_contribution`、`dom_access`、`client` | 对于手动导入的文件，无论是否同意都会被**直接丢弃** |

它们恰好只在一个 id 上有区别：`push_to_ui` 值得拥有一个勾选框，但不值
得因为它就拒绝一个用户刻意选择导入的文件 —— 它只会把事件推送进插件
自己的面板中，不会去任何别的地方。这两份清单都定义在
`astra-plugin-manifest/src/permissions.rs` 中，守护进程、CLI 和注册表
全都从那里读取，所以不可能悄悄冒出第三份清单来。

一个需要这四种被拒绝权限之一的插件，无法通过这种方式交付。它可以
[在开发期间被侧载(sideload)](sideload.md)，或者走正式上架流程。

## 在任何东西被写入之前先征求同意

`InspectPluginFile` 会**不安装地**读取清单文件：不会解压任何东西，
不会启动任何东西，不会写入任何信任记录，也不会把归档中的任何字节
复制出来。文件在内存中被解析然后关闭。调用它之后如果一直不导入，
机器会完全保持原样。

正是这一点让 Astra 能够在你做出任何承诺之前，展示出和商店路径完全
相同的那份权限说明。

## 相比商店，你会失去什么

| | 商店 | 导入的文件 |
|---|---|---|
| 字节内容经注册表反签名 | 有 | 没有 |
| 作者被固定，所以来自不同仓库的更新会被拒绝 | 有 | 没有 |
| 撤回(失效)能够触达到你 | 有（一旦信任链锚定完成） | 没有 |
| 更新 | 自动进行，附带权限变更审阅 | 你自己去找下一个文件 |
| 高风险权限 | 可用，需经同意 | **四种被拒绝** |
| 验证失败 | 硬性拦截，无法覆盖(override) | 归档本身的校验依然适用 |

计划中提到，当一个被导入文件的摘要值在一份全新的索引中出现时，可以把
它提升为完全信任。**这个提升机制尚未实现** —— 一次导入在它的整个生命
周期内都会停留在第 2 层级。

## 在导入别人发给你的东西之前

插件是一个拥有你完整用户权限的原生进程。这里没有沙箱。导入一个文件，
是你在对发送它的那个人做出的一个判断，而不是对这个文件本身。
[安全模型](../1-orientation/security.md) 说明了这些机制能证明什么、
不能证明什么。

如果这是你自己的插件，而你还在编写它，你真正想要的是
[`astra-plugin dev`](sideload.md)，而不是这个。

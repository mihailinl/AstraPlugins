# ローカルの `.astraplugin` ファイルをインストールする

**上級者向けであり、4 つのパーミッションを失います。** このページは、
帯域外で届いたバンドル — 同僚から送られてきた、自分でビルドした、
まだリストに掲載されていないリリース — をインポートすることについて
説明します。これはプラグインのインストール方法ではありません;
[それはストアです](get-listed.md)。ストアではアーティファクトはダイジェスト
で固定され、検証失敗はハードブロックです。

> **このファイルを誰かに渡すことは、あなたのプラグインを公開すること
> ではありません。** あなたがビルドして送ったバンドルにはビルド証明も
> レジストリレコードもないため、送った先の 1 台のマシンで低い階層で
> インストールされ、それ以外の誰にも届きません。公開とは、CI がビルド
> して証明するタグ付きリリースに、1 回のリスティング申請を加えたもの
> です — [全行程は 1 ページ](../publishing.md) にまとまっています。

## それが何か

`PluginService.ImportPluginFile` は **`.astraplugin` ファイルへの
パス**を取ります — バイト列ではなく、ディレクトリでもありません。
Astra の UI は、あなたがファイルを選ぶとこれを呼び出します。

バンドルは、最初の無圧縮(stored)エントリとして `MANIFEST.json` を持つ
ZIP です。デーモンはすべてのダイジェストを再計算し、ファイル一覧が両方
向で網羅的であることを確認し、一致しないものは何であれ拒否します。
`astra-plugin verify` はローカルで同じチェックを実行するので、誰かから
送られたファイルをインポートする前に実行すべきです
([CLI をインストールする](../install-cli.md)を持っていない場合は先に
インストールしてください):

<!-- doctest: cli -->
```bash
astra-plugin verify some-plugin-0.3.0-linux-x64.astraplugin
```

## 上限: 4 つのパーミッションが無条件で拒否される

インポートされたファイルにはカタログレコードがないため、そのバイト列に
副署名するものは何もなく、その作者を固定するものも何もありません。
これは**ティア 2** でインストールされ、そのティアの上限は警告では
ありません — パーミッションは**落とされます**:

| マニフェストが何を要求していても拒否される | 理由 |
|---|---|
| `send_chat_message` | ユーザーが話したかのように AI のターンを駆動する |
| `set_theme_contribution` | アプリ全体のスタイルを変更する |
| `dom_access` | Astra ウィンドウ内でプラグインのコードを実行する |
| `client` | 独自のセッションを持つチャットフロントエンドになる |

`fire_trigger`、`subscribe_events`、`set_variable`、`push_to_ui` は
この上限を生き延びます — これらは語彙の中の**低リスク**な端であり、
だからこそこれらを通すのにリスト掲載による保証が不要なのです。この
4 つのうち `push_to_ui` だけが独自の同意チェックボックスを持ちます。

この 2 つのリストは意図的に異なっており、どちらがどちらかを正確に
理解しておく価値があります:

| リスト | メンバー | 何を決めるか |
|---|---|---|
| `HIGH_RISK_PERMISSIONS` | `send_chat_message`、`push_to_ui`、`set_theme_contribution`、`dom_access`、`client` | どのインストール経路でも、それぞれが**独自の同意チェックボックス**を得る |
| `TIER2_REFUSED_PERMISSIONS` | `send_chat_message`、`set_theme_contribution`、`dom_access`、`client` | 手動でインポートされたファイルからは、同意の有無にかかわらず**無条件で落とされる** |

この 2 つはちょうど 1 つの id だけ異なります: `push_to_ui` はチェック
ボックスに値するものの、ユーザーが意図的に選んでインポートしたファイル
を拒否するには値しません — それはプラグイン自身のパネルにのみイベント
を push し、他のどこにも影響しません。どちらのリストも
`astra-plugin-manifest/src/permissions.rs` にあり、デーモン、CLI、
レジストリのすべてがそこから読み取るため、第 3 のリストが勝手に生まれる
ことはあり得ません。

拒否される 4 つのいずれかを必要とするプラグインは、この方法では配信
できません。[開発中にサイドロードする](sideload.md)か、リストに掲載
してもらってください。

## 何かが書き込まれる前の同意

`InspectPluginFile` は**インストールせずに**マニフェストを読みます:
何も展開されず、何も起動せず、信頼レコードは書き込まれず、アーカイブ
からバイト列がコピーされることもありません。ファイルはメモリ内でパース
され、閉じられます。これを呼び出してから一度もインポートしなければ、
マシンはまったく元のままです。

これにより、Astra はあなたが何かを確約する前に、ストア経路と同じ
パーミッションシートを表示できます。

## ストアと比べて何を失うか

| | ストア | インポートされたファイル |
|---|---|---|
| レジストリによって副署名されたバイト列 | あり | なし |
| 固定された作者、そのため別リポジトリからの更新は拒否される | あり | なし |
| 撤回(失効)があなたに届く | あり(チェーンが固定されれば) | なし |
| 更新 | 自動、パーミッション変更のレビュー付き | あなた自身が次のファイルを見つける |
| 高リスクパーミッション | 同意付きで利用可能 | **4 つが拒否される** |
| 検証失敗 | ハードブロック、オーバーライドなし | アーカイブのチェックは引き続き適用される |

計画には、インポートされたファイルのダイジェストが新しいインデックス
に現れたときに、それをフル信頼へ昇格させることが記述されています。
**その昇格は実装されていません** — インポートは、その生涯を通じて
ティア 2 のままです。

## 誰かから送られたものをインポートする前に

プラグインは、あなたのフルユーザー権限を持つネイティブプロセスです。
サンドボックスはありません。ファイルをインポートすることは、そのファイル
についてではなく、それを送ってきた人物についての判断です。
[セキュリティモデル](../1-orientation/security.md) は、これらの仕組みが
証明することと証明しないことを述べています。

もしそれがあなた自身のプラグインで、まだ書いている途中なら、これでは
なく [`astra-plugin dev`](sideload.md) が欲しいものです。

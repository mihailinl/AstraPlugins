# パフォーマンスと制限

このページのすべての数値は、1 つのファイルで 1 回だけ宣言され、それを
必要とする場所に生成されています。どれも推測ではありません。

## 共有の制限値

[`spec/limits.yaml`](../../../spec/limits.yaml) は、デーモンと SDK の
間で同一でなければならない数値が書き込まれている唯一の場所です。
`node tools/gen-limits.mjs` は 3 つの SDK すべての定数を再生成し、
デーモンのコピーの隣にある `const _: () = assert!(…)` は、デーモンも
同様に移動するまでビルドに失敗します。この動機となったバグ: ストリーミング
STT のオーディオチャンネルが、デーモンでは 500 で Rust SDK では 32 で
あり、この不一致がすべての発話を静かにその最初の一部分に切り詰めて
いました。

| 制限 | 値 | 何を制限するか |
|---|---|---|
| `plugin_start_timeout_secs` | **20** | spawn からプラグインの最初の出力行まで。これを超えるとデーモンは起動を失敗と判断し、プロセスを回収します |
| `plugin_stop_grace_secs` | **5** | `Shutdown` からプロセスグループが kill されるまで。あなた自身のドレイン(後始末)予算はこれより短くなければなりません。そうでなければ、あなたの片付け経路が実行される前にデーモンがあなたを kill します |
| `stt_audio_channel_capacity` | **500** | デーモンの音声パイプラインとあなたの `stt` フックの間で、両端でバッファされるチャンク数。約 10 秒の音声: 最悪ケースのウェイクワードシード バーストと、遅いプロバイダがまだ推論している間に届くライブ音声を合わせた分 |
| `max_extract_bytes` | **524 288 000**(500 MiB) | デーモンが 1 つのアーカイブから展開する非圧縮の合計サイズ |
| `max_archive_entries` | **10 000** | 1 つのアーカイブ内のエントリ数 |

最後の 2 つは zip 爆弾の緩和策であり、パッケージング上の制約でもあり
ます: いずれかを超えるバンドルはインストール不可能なプラグインになる
ため、CLI はユーザーのマシンで発見させるのではなく、ビルド時に拒否
します。

## `call_timeout_secs` — あなたが設定するもの

マニフェスト内の `plugin.call_timeout_secs` は、デーモンが `CallTool`
と `ExecuteAction` を諦めるまでどれだけ待つかです。未設定の場合、
デーモン自身の `PLUGIN_CALL_TIMEOUT` が使われます。これは意図的に
「永遠」より低く設定されています。

**長時間実行されるエージェントの前面に立つプラグインは、これを宣言し
なければなりません。** そうしないと、あなたのサブプロセスが実行を続けて
いる間に、デーモンはあなたの結果を捨ててしまいます — ユーザーには失敗
が見え、マシンは処理を続けます。

<!-- doctest: toml-manifest -->
```toml
[plugin]
id = "coding-agent"
name = "Coding Agent"
version = "0.1.0"
license = "MIT"
author = "You"
# This plugin runs an agent that can legitimately take minutes.
call_timeout_secs = 180

[entry]
command = "bin/coding_agent"

[capabilities]
tools = true
```

これはプラグインごとの設定であり、MCP サーバーのタイムアウトがサーバー
ごとであるのと同じです。思いつく最大の数字ではなく、あなたの最も遅い
正当な呼び出しが必要とする値に設定してください: このタイムアウトは、
固まったプラグインが会話をハングさせるのを止めるものでもあります。

## 言語ごとの起動予算

20 秒は寛容な数字ですが、3 つの言語のうち 2 つは今もそれを使い切って
しまいます。

| | 典型的なコールドスタート | それを食いつぶすもの |
|---|---|---|
| Rust | ミリ秒単位 | 何もありません |
| TypeScript | Node のコールドスタート | バンドルは単一ファイルなので、ツリー全体にわたるモジュール解決がありません |
| Python | インタプリタ + `grpcio` の import | モジュールスコープでインポートされる大きな依存関係 |

修正方法はどちらのインタプリタ型の場合でも同じです: **必要とする
フックの中で遅延インポートしてください。** `on_start` でロードするモデル
は、プラグインが生きる前にユーザーが待つことになるモデルです; 最初の
呼び出しでロードするモデルは、ユーザーが 1 回だけ待つことになるモデル
です。

`astra-plugin test` はあなたのマシン上での実際の数値を測定し、予算に
対してそれを出力します:

<!-- doctest: output from="astra-plugin test . --no-build" -->
```
  [ok  ] the plugin says something before the daemon gives up: first line on stdout after 792.4µs
         (the daemon waits 20s, spec/limits.yaml plugin_start_timeout_secs)
  [ok  ] Shutdown is honoured within the grace period: the process exited 42.5ms after Shutdown
         (grace is 5s, spec/limits.yaml plugin_stop_grace_secs)
```

## 猶予期間内でのシャットダウン

`Shutdown` に応答した後、あなたは終了します。5 秒後、プロセスグループ
が kill されます。フラッシュしなければならないもの — ファイル、上流
セッション — は、その窓の中でフラッシュするか、まったくしないかの
どちらかです。

デーモン全体のシャットダウンは、全体の解体期限によって制約される
**はるかに短い**猶予を渡します。5 秒を使い切ってよい予算として扱わ
ないでください; それより十分下であるべき上限として扱ってください。

## ヘルスチェック

`HealthCheck` は 15 秒ごとに実行されます。これはデーモンの任意フック
ヘルパーを経由してルーティングされていないため、`UNIMPLEMENTED` を
含む**あらゆる**エラーがプラグインを死んでいるとマークします。これを
オーバーライドする場合は、それを安価にし、かつ完全なものにしてください:
上流サービスを呼び出すヘルスチェックは、そのサービスの障害をあなたの
プラグインが死んでいるとマークされることに変えてしまいます。

## バンドルサイズ

展開制限を超えて最大値を強制するものはありませんが、知っておく価値の
ある 2 つのことがあります:

- Rust のバンドルは strip されたリリースバイナリであり、通常は数
  メガバイトです。
- TypeScript のバンドルは `node_modules` を**出荷しません** —
  `astra-plugin build` は単一の自己完結型 CommonJS ファイルを生成し、
  CI は実行時にモジュールを求めて手を伸ばすものが何も残っていないこと
  をアサートします。

再現可能なパッキング(`--reproducible`)は、エントリの順序、mtime、
圧縮レベルを固定するため、同じ入力からの 2 回のビルドはバイト同一に
なります。リリースワークフローはすべてのリリースでカナリアを実行して
おり、これがサードパーティによる再ビルドを意味あるものにしています。

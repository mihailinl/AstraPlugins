# `.astraplugin` バンドル形式、バージョン 2 — 規範仕様

**ステータス:** 規範的。この文書はバイト列を定義します。このリポジトリ
を一度も見たことがない第三者が、これだけを頼りに検証ツールを実装し、
[`testdata/bundles/`](../../../testdata/bundles/README.md) 内のすべて
のファイルについて私たちと同じ判定を得られるように書かれています。

**スキーマ文字列:** `astra.bundle/2`
**ファイル拡張子:** `.astraplugin`
**メディアタイプ:** 登録なし; `application/octet-stream` として配信され
ます。

要求語 — **MUST**、**MUST NOT**、**SHOULD**、**MAY** — は RFC 2119 に
従います。「Reject(拒否)」とは: バンドル全体を拒否し、展開せず、より
古い形式へのフォールバックも行わないことを意味します。この形式に部分的
な受け入れはありません。

---

## 0. この形式が何であり、何でないか

v2 バンドルは、**最初のエントリが、他のすべてのエントリを名指しして
ダイジェストするマニフェストである** ZIP アーカイブです。それがこの
アイデアのすべてです。これによって、v1 バンドル(`plugin.toml` を含む
ただの ZIP)にはできなかったことが 1 つ可能になります: リーダーは、
アーカイブ自身の構造をまだ何も信頼していない段階で、そのアーカイブが
何を含むことを*許可されているか*を知ることができ、ディスクに書き込まれ
るすべてのファイルがそのリストと照合されます。

この形式が意図的に**行わない**3 つのことを、読者がダイジェストの存在
から推測してしまわないよう、ここに明記します:

* **それ自身の真正性を運びません。** v2 バンドルの内部には、誰がそれ
  を生成したかを証明するものは何もありません。真正性はファイルの外部
  から来ます: `sha256(ファイル全体)` に対する GitHub のビルド証明、
  そして同じ数値を固定する署名済みレジストリインデックス
  ([`registry-index.md`](registry-index.md))です。旧来の ZIP 内
  `SIGNATURE`/`PUBKEY` ペア(§11)は例外*ではありません* — それは
  廃止予定であり、決して信頼のシグナルにはなりません。
* **実行時にプラグインが何をしてよいかについては何も述べません。**
  それは [`permissions.md`](permissions.md) の役目です。
* **サンドボックスの境界ではありません。** インストールされたプラグイン
  はユーザーのフル権限で動くネイティブプロセスです。バンドルを検証する
  ことは、そのバイト列が作者が公開したバイト列であることを教えますが、
  それらのバイト列が実行されたときに何をするかを制約するものではあり
  ません。

## 1. 準拠と、どの実装が規範的か

この形式を読む 3 つのプログラムがあります:

| | 実装 | 役割 |
|---|---|---|
| **CLI** | `astra-plugin-cli/src/bundle.rs`(`BundleBuilder`、`Bundle::open`) | バンドルを書く; `astra-plugin verify` はそれを読み戻す |
| **daemon** | `Astra/astra-rs/astra-daemon/src/plugins/bundle.rs`(`inspect`、`BundleManifest::check_structure`) + `ops/install_plugin.rs`(`extract_archive`) | 見知らぬバイト列がユーザーのディスクに展開されるかどうかを決める |
| **registry** | `astra-registry/bot/lib/bundle.mjs`(`inspectBundle`) | リスト掲載を公開するかどうかを決める |

**この文書が規範的であり、どの実装も規範的ではありません。** 実装が
この文書と食い違う場合、その実装にバグがあります。2 つの実装が互いに
食い違う場合、その食い違いは `testdata/bundles/vectors.json` に名前の
付いた分岐として記録され、§14 で再現されます — そこにある `verdict`
フィールドが正しい答えであり、`expect` フィールドは今日各プログラムが
実際に行っていることです。

4 つ目の実装への帰結: **3 つのプログラムのどれかではなく、§13 を実装
してください。** デーモンを正確に再現する検証ツールは分岐 F2 を引き
継ぎ、レジストリを再現するものは F3 を引き継いでしまいます。

## 2. コンテナ

* バンドルは、従来のリーダーで読める ZIP アーカイブで**なければなり
  ません**: オフセット 0 からのローカルファイルヘッダー、セントラル
  ディレクトリ、セントラルディレクトリ終端レコード。
* **エントリ 0 に ZIP64 を使用してはいけません(MUST NOT)。** ローカル
  ヘッダーが ZIP64 のサイズセンチネル `0xFFFFFFFF` を宣言している
  `MANIFEST.json` は拒否されます(§4)。他のエントリに宣言された
  ZIP64 の制限はありません; それほど大きなマニフェストは、もはや
  マニフェストではありません。
* エントリは**ファイルのみ**です。ディレクトリエントリは拒否されます
  (§6.5): ディレクトリはパスによって暗示されるものであり、ダイジェスト
  を運ぶことができません。
* **エントリ 0 は `MANIFEST.json` で、無圧縮(圧縮方式 0)で格納されて
  いなければなりません(MUST)。** 他のすべてのエントリは方式 0(格納)
  または方式 8(deflate)を使用してもかまいません(MAY)。CLI は
  マニフェスト以外をすべてレベル 6 の deflate でパックします;
  `testdata/bundles/` 内のベクタはすべて格納方式です。どちらも準拠して
  います。
* 順序: `MANIFEST.json` が最初; 旧来の `SIGNATURE`/`PUBKEY` ペアが存在
  する場合は最後にその順で(§11); それ以外はその間です。プロデューサー
  は中間部分をパスのバイト辞書順で書くべきです(SHOULD) — CLI はそう
  します。そのエントリは `BTreeMap` に保持されているからです — しかし
  検証ツールはそれを要求してはいけません(MUST NOT)。*マニフェスト*
  の `files` 配列はソートされており、その要件は強制されます(§7.4)が、
  アーカイブ自身の順序はそうではありません。
* タイムスタンプには意味がありません。CLI はすべてのエントリに
  `1980-01-01T00:00:00`(DOS タイムスタンプが表現できる最も早い日付)
  を刻印し、同じ入力からの 2 回のビルドが同じバイト列を生成するように
  します。検証ツールはタイムスタンプを読んではいけません(MUST NOT)。

## 3. 2 つのダイジェスト

この形式には正確に 2 つのダイジェスト構成が存在します。どちらも
SHA-256 であり、どちらも**64 文字の小文字 16 進数**として描画され、
どちらも大文字小文字を区別せずに比較されることは決してありません。

### 3.1 アーティファクトダイジェスト

```
artifact_digest = SHA256(the entire .astraplugin file, byte for byte)
```

正規化なし、エントリ走査なし、除外なし。これは正確に 3 か所に現れる
数値であり、その 3 か所すべてで同じ数値です:

1. GitHub ビルド証明の主体、
2. 署名済みレジストリインデックスの `artifacts.<platform>.sha256`、
3. デーモンがアーカイブを開く前にストリームしてハッシュするもの。

これは(`sha256:` プレフィックスなしで)裸で書かれます。なぜなら、
これが現れるすべての場所はすでに型付けされているからです。

### 3.2 マニフェストダイジェスト — そしてなぜドメイン分離されているか

```
manifest_digest = SHA256( "astra.bundle/2" ‖ 0x00 ‖ MANIFEST.json bytes )
```

このプレフィックスは 14 バイトの ASCII `astra.bundle/2` に続けて 1 つ
の `0x00` バイト — 合計 15 バイト — であり、その直後にエントリ 0 の
*格納された*バイト列が、アーカイブ内にあるとおり、再シリアライズなし、
空白の正規化なし、末尾改行の調整なしで続きます。

**なぜこのプレフィックスが存在するか。** これがなければ、この構成は
`SHA256(何らかのバイト列)` になります — これは、同じ文書内のすべての
`files[].sha256` とまったく同じ形です。両者は、同じレコードを通って
やってくる、区別できない 64 桁の 16 進数文字列になってしまい、ある
コンテキストから持ち出された値が別のコンテキストで検証されてしまい
ます。このプレフィックスは、マニフェストダイジェストを同じバイト列に
対する別の関数にします。

**具体例**(ベクタ `ok-minimal`、`testdata/bundles/handcheck.sh
ok-minimal` で再現可能 — これは `dd`、`od`、`printf`、`cat`、
`sha256sum` だけを使います):

```
sha256(manifest bytes)                    2e16024e4557332a2a404a89a94b124807e0b4741046e29fc3f6b94ea1b69682
sha256("astra.bundle/2\0" ‖ manifest)     8e88f82cc6dbb9c253e3a4409a03f763668ca1a46439f994e2a45a6da23ccaf4
sha256(whole file)                        ac3d49a2fc2b7408d5b3c805ec91541510c272547a16e3bc7a30f269ba801aed
```

2 番目の値が期待される場所で 1 番目の値を生成する実装は、プレフィックス
を忘れています。`vectors.json` はすべてのベクタについて両方の数値
(`manifest_sha256` と `manifest_digest`)を記録しているため、これは
1 行のチェックであり、この 2 つは実在するどんなマニフェストでも
**決して**等しくなりません。

### 3.3 廃止された構成、そしてそれを廃止させた衝突

v2 以前、バンドルは以下に対する ZIP 内 `SIGNATURE` によって認証されて
いました

```
legacy_digest = SHA256( name₀ ‖ content₀ ‖ name₁ ‖ content₁ ‖ … )
```

ZIP インデックス順で、`SIGNATURE` と `PUBKEY` 自身はスキップします。
区切り文字なし、長さプレフィックスなし、エントリ数なし、ドメイン分離子
なし。この構成は**曖昧**であり、その曖昧さはこのリポジトリ内に 2 つの
凍結されたファイルとして存在します:

| ベクタ | アーカイブが保持するもの | 寄与するもの |
|---|---|---|
| `collision-a-bc` | エントリ `a`、内容 `bc` | `a` ‖ `bc` = `abc` |
| `collision-ab-c` | エントリ `ab`、内容 `c` | `ab` ‖ `c` = `abc` |

この 2 つのアーカイブは**バイト単位で同一の `MANIFEST.json`**を運び、
したがって同一の `manifest_digest` を持ちます; それらのアーティファクト
ダイジェストは異なります; そしてそれらの旧来のダイジェストは 1 つの
数値です:

```
legacy_concat_sha256   0c0e28712aad8b042598cfb95b52d201b955b4c4942e87680404aa446f96e817   (both)
```

1 つの `SIGNATURE` が両方のアーカイブを認証してしまい、その方式を
使う検証ツールは、自分がどちらを保持しているかを判別できません。

v2 の下ではこの 2 つは分離されており、それには網羅性チェックの**両方向
とも**が必要です(§7.1): `collision-ab-c` では、`ab` はどのマニフェスト
行もカバーしないアーカイブエントリであり、*かつ*、`a` はどのアーカイブ
エントリも満たさないマニフェスト行です。「listed ⇒ present」だけを
チェックする検証ツールはこれを受理してしまいます。

`legacy_concat_sha256` はこの 1 つの目的のためだけに `vectors.json` に
記録されています。このプロジェクト内の何ものも、他の目的でこれを計算
すべきではありません。

## 4. エントリ 0、バイト単位で

準拠するリーダーは、何も伸長(inflate)せず、セントラルディレクトリを
読まずに、ファイルの先頭部分から `MANIFEST.json` を取得できなければ
なりません(MUST)。これが、攻撃者に制御された構造をまだ信頼していない
段階で、リーダーがアーカイブの許可された内容を知ることを可能にする性質
です。3 つの実装すべてがまさにこれを行います(CLI とデーモンの
`manifest_from_local_header`、レジストリの
`manifestBytesFromLocalHeader`)。

オフセット 0 のローカルファイルヘッダーを読みます。すべてのマルチバイト
フィールドはリトルエンディアンです。

| offset | size | フィールド | 要件 |
|---|---|---|---|
| 0 | 4 | シグネチャ | `0x04034B50` でなければならない(MUST)、さもなくば拒否: ZIP ではない |
| 6 | 2 | 汎用フラグ | ビット 0(暗号化)は 0 でなければならない; ビット 3(データディスクリプタ)は 0 でなければならない |
| 8 | 2 | 圧縮方式 | 0(格納)でなければならない |
| 18 | 4 | 圧縮サイズ | `0xFFFFFFFF`(ZIP64 センチネル)であってはならない; 4 MiB 以下でなければならない |
| 26 | 2 | ファイル名長 `n` | — |
| 28 | 2 | 拡張フィールド長 `e` | — |
| 30 | `n` | ファイル名 | 正確に 13 バイトの `MANIFEST.json` でなければならない |
| 30+`n`+`e` | size | マニフェストのバイト列 | — |

**苦情の順序は実装と同じにしてください:** 他の何よりも先に*名前*を
チェックしてください。エントリ 0 が別のファイルであるアーカイブは、
そのファイルがたまたま失敗するヘッダーチェックのどれかで引っかかり、
*それ*を報告することは、リーダーを、持っていないマニフェストの問題を
探すよう仕向けます。

これが生む拒否とそのベクタ:

* エントリ 0 が `MANIFEST.json` でない → `manifest-not-first`。
* エントリ 0 が圧縮されている → `manifest-compressed`。
* サイズがファイルの終端を超える → 切り詰められたバンドル。

**どこかに `MANIFEST.json` を含むバンドルを、v2 以前のバンドルとして
読んではいけません(MUST NOT)。** マニフェストが存在するがエントリ 0
でない場合、答えは拒否であり、より弱いルールへのフォールバックでは
決してありません。そうでなければ、1 つのエントリを移動するだけで、
v2 が追加する唯一のもの、ファイルごとのハッシュを無効化するのに十分
になってしまいます。(`manifest-not-first` は、すべての実装をこれに
従わせるために存在します。)

### 4.1 セントラルディレクトリは一致しなければならない

エントリ 0 は 2 回存在します: 1 回はオフセット 0 のローカルヘッダー
として、もう 1 回は ZIP リーダーが使うセントラルディレクトリのレコード
としてです。ZIP 形式には、それらが同じバイト列を記述することを強制
するものは何もありません — セントラルディレクトリは最後に追加される
からです。

検証ツールは、マニフェストを*両方の*経路で読み、比較しなければなりま
せん(MUST):

* CLI とレジストリは 2 つのバイト文字列/それらのダイジェストを比較
  します;
* デーモンは ZIP リーダー経由でエントリ 0 を読み、それをオフセット 0
  から持ち上げたバイト列と比較します。

ベクタ: `header-disagree`。これは v2 に固有な攻撃の中で最も特徴的な
ものです。チェックしなければ、レジストリはどのデーモンも決して強制
しないマニフェストをハッシュし、表示し、副署名してしまいます。

**一致するときにどのバイト列がダイジェストされるか:** オフセット 0
のバイト列です。一致しない場合はバンドルが拒否されるため、この問い
自体が生じません。

## 5. `MANIFEST.json`

UTF-8 の JSON、1 つのオブジェクトです。CLI は末尾に改行を付けて整形
して書き出します; ダイジェストは実際に書かれたバイト列に対するもの
なので、フォーマットはプロデューサーの選択であり、検証ツールはハッシュ
する前に再シリアライズしてはいけません(MUST NOT)。

完全な例 — ベクタ `ok-minimal`、`2e16024e…` にハッシュされる正確な
バイト列:

```json
{
  "schema": "astra.bundle/2",
  "plugin_id": "vector-plugin",
  "version": "1.0.0",
  "platform": {
    "os": "linux",
    "arch": "x86_64"
  },
  "protocol": 1,
  "min_astra_version": "",
  "capabilities": [
    "tools"
  ],
  "permissions": {},
  "permissions_hash": "sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a",
  "entry": {
    "command": "./bin/fixture",
    "args": []
  },
  "files": [
    {
      "path": "bin/fixture",
      "sha256": "0f7ceb62618162c2ac6765ac683e65dc81ad19add148ada1e7186d186847caba",
      "size": 33,
      "mode": "0755"
    },
    {
      "path": "plugin.toml",
      "sha256": "da1141bb5c5390f1c8a646a0e0b0be1f26cdc0862ccb850dd86e0cd0238f3117",
      "size": 218,
      "mode": "0644"
    }
  ]
}
```

### 5.1 フィールド

| フィールド | 型 | プロデューサー | 検証ツール |
|---|---|---|---|
| `schema` | string | `"astra.bundle/2"` でなければならない | 正確に比較しなければならない; それ以外の値 → 推測せず拒否 |
| `plugin_id` | string | プラグイン id、`plugin.toml` と一致 | §9 |
| `version` | string | semver | レジストリとデーモンによってリスト掲載と照合される |
| `platform` | `{os, arch}` | §5.2 参照 | ホスト互換性チェックは形式のものではなくインストーラのもの |
| `protocol` | integer ≥ 0 | プラグインが話す wire プロトコル | 範囲チェックはホストのもの |
| `min_astra_version` | string | semver、または要件なしを表す `""` | — |
| `capabilities` | array of string | デーモンのケーパビリティ語彙 | — |
| `permissions` | object | `plugin.toml` の `[permissions]` セクション、そのまま | §10 |
| `permissions_hash` | string | §10 の正規バイト列に対する `"sha256:" ‖ hex` | §10 |
| `entry` | `{command, args}` | §8 | §8 |
| `files` | array | §7 | §7 |

**プロデューサーは上記のすべてのフィールドを発行しなければなりません
(MUST)。** 検証ツールは、`schema`、`plugin_id`、`version`、
`platform`、`entry`、`files` のいずれかを欠くマニフェストを拒否しな
ければなりません(MUST)。

*分岐、隠すのではなく明記します:* デーモンは、`protocol`、
`min_astra_version`、`capabilities`、`permissions`、
`permissions_hash` が存在しない場合にデフォルト値を与えます
(`#[serde(default)]`); CLI のリーダーはそれらを要求します。したがって、
これらのいずれかを省略したバンドルはインストール可能でありながら
`astra-plugin verify` では検証不可能です。そのようなものを生成しない
でください。

**未知のメンバーは受け入れられ、無視されなければなりません(MUST)。**
将来の v2 の追加(例えば `changelog_url`)が、それを運ぶすべてのバンドル
を古いホストでインストール不可能にしてはいけません。スキーマの引き上げ
なしに変わり得ないのは、上記フィールドの*意味*です — そして `schema`
は正確に比較され、これがそれを制約します。

### 5.2 `platform`

```json
{"os": "linux",   "arch": "x86_64"}     → registry platform key  linux-x64
{"os": "windows", "arch": "x86_64"}     → registry platform key  windows-x64
{"os": "any",     "arch": "any"}        → registry platform key  noarch
```

ある軸での `any` は「要件なし」を意味します: バンドルは、`(os ==
"any" || os == host_os) && (arch == "any" || arch == host_arch)` の
とき、ホストと互換性があります。`noarch` は、すべての TypeScript と
Python のプラグインが出荷される方法です — ソースまたはバイトコードで、
ホストがすでに持っているランタイムによって実行されます — そして
レジストリは 1 つに対してサポートされているすべてのプラットフォーム
キーの下に同じ URL とダイジェストを書き込むため、どのクライアントも
この言葉を学ぶ必要がありません。ベクタ: `ok-noarch-runtime`。

今日、他のどんな `{os, arch}` の組も対象を名指ししません。
`linux-arm64`、`windows-arm64`、`macos-x64`、`macos-arm64` はレジストリ
のスキーマ内で予約されたプラットフォームキーです; Astra はそれらの
ためのデーモンを出荷していません。

## 6. エントリ名

すべてのアーカイブエントリ名がチェックされます。これらのルールが
存在するのは、エントリ名が他の誰かのファイルシステム上のパスになる
ためであり、それを読むのは展開ツールだけではないためです。

エントリ名は、以下のいずれかが成り立つ場合に**拒否されます**:

1. **空**である。
2. **バックスラッシュ** `\` を含む。ZIP パスは `/` のみを使用します;
   バックスラッシュは Windows ではパス区切り文字であり、他の場所では
   リテラルなファイル名文字です。
3. **絶対パス** — `/` で始まる。
4. **`:`** を含む。NTFS では `bin/fixture:stream` は代替データストリーム
   として `bin/fixture` の*中に*目に見えない形で書き込まれます。
   ベクタ: `path-ads`。
5. **制御文字**(U+0000–U+001F、U+007F)を含む。
6. **空のコンポーネント**(`a//b`)、または **`.`** もしくは **`..`**
   に等しいコンポーネントを持つ。ベクタ: `path-traversal`
   (`../escape`)。
7. **ドットまたはスペース**で終わるコンポーネントを持つ。Win32 は
   どちらも黙って取り除くため、`bin/fixture.` と `bin/fixture` は
   2 つのエントリでありながら 1 つのファイルになります。ベクタ:
   `path-trailing-dot`。
8. コンポーネントの**幹**(最初の `.` の前のテキスト、大文字小文字を
   区別せず比較)が予約された MS-DOS デバイス名である: `con`、`prn`、
   `aux`、`nul`、`com1`–`com9`、`lpt1`–`lpt9`。`CON.txt` もコンソール
   です。

加えて:

9. **重複した名前は拒否されます**。厳密にも**大文字小文字を区別せず
   にも**です: `plugin.toml` と `Plugin.TOML` は、ZIP リーダーにとって
   は 2 つのエントリですが、NTFS と APFS では 1 つのファイルであり、
   2 番目が、1 番目がハッシュされた*後に*それを上書きします。ベクタ:
   `duplicate-entry`、`duplicate-entry-case`(分岐 F1 参照)。
10. **ディレクトリエントリは拒否されます**(§2)。エントリは、その名前
    が `/` で終わる場合、または外部属性が `mode & 0o170000 ==
    0o040000` を持つ Unix モードを与える場合、ディレクトリです。両方
    をチェックしてください: 前者は ZIP ライターが慣習的に発行する
    もの、後者は悪意のあるものが代わりに発行し得るものです。
11. **シンボリックリンクエントリは拒否されます**: 外部属性が
    `mode & 0o170000 == 0o120000` を持つ Unix モードを与えるエントリ
    です。ここでの脱出はリンクの*ターゲット*にあり、これはエントリの
    *内容*です — 上記のすべてのパスルールは名前を検査するものであり、
    どれもそれを見ることはできません。ベクタ: `symlink-entry`。

これらのルールは、`MANIFEST.json`、`SIGNATURE`、`PUBKEY` を含む
**すべての**エントリに適用されます。

## 7. `files` — アーカイブが照合される対象のリスト

`files` はオブジェクトの配列です:

| メンバー | 型 | ルール |
|---|---|---|
| `path` | string | アーカイブエントリ名; §6 に従う |
| `sha256` | string | **正確に 64 文字の小文字 16 進数**、プレフィックスなし |
| `size` | integer ≥ 0 | 非圧縮バイト長 |
| `mode` | string | 4 桁の 8 進数、例: `"0755"` — *文字列*です。なぜなら JSON には 8 進数リテラルがなく、10 進数の `755` は別のモードだからです |

* 大文字の 16 進数を含む `sha256` は、丸め込まれるのではなく**拒否
  されます**。ここのダイジェストは文字列として比較されるため、大文字
  のものは何とも一致せず、不正なマニフェストではなく壊れたファイルと
  して現れます。ベクタ: `uppercase-digest`。
* `mode` は 8 進数としてパースできなければなりません(MUST)。先頭の
  `0o` はデーモンのパーサーによって受け入れられます; プロデューサーは
  それを発行してはいけません(MUST NOT)。`"0788"` は拒否されます —
  8 は 8 進数の桁ではありません。
* 同じ `path` が 2 回現れてはいけません(MUST NOT)。
* 予約された名前(`MANIFEST.json`、`SIGNATURE`、`PUBKEY`)は現れては
  いけません(MUST NOT): マニフェストは自身のダイジェストを一覧
  できず、旧来のペアは一覧されたファイル*に対して*計算されます。

### 7.1 両方向の網羅性

`Listed` を `files[].path` の集合、`Present` を上記 3 つの予約名を
除いたアーカイブエントリ名の集合とします。検証ツールは以下を強制
しなければなりません(MUST):

```
Present ⊆ Listed     (no archive entry that the manifest does not list)
Listed ⊆ Present     (no listed file that the archive does not contain)
```

常に両方です。片方だけでは穴になります:

* `Listed ⊆ Present` だけをチェックすると、攻撃者は展開ツールが書き
  込むがハッシュされないエントリを**追加**できてしまいます — ベクタ
  `extra-file`(`bin/backdoor`);
* `Present ⊆ Listed` だけをチェックすると、攻撃者はエントリを
  **削除**しながらバンドルを無傷だと主張できてしまいます — ベクタ
  `missing-file`。

そして、衝突ペア(§3.3)を分離するのはこの連言です。

### 7.2 コンテンツダイジェスト

`Present` 内のすべてのエントリについて: そのエントリの**非圧縮内容**
の SHA-256 は、その `files` 行の `sha256` と等しくなければなりません
(MUST)。ベクタ: `content-digest-mismatch` — 正しいファイル集合、正しい
長さ、間違ったバイト列。これが、差し替えられたバイナリを引っかける
チェックです。

これが*いつ*実行されるかは実装の選択であり、1 つの厳格な制約があり
ます: ハッシュされるバイト列は、ディスクに書き込まれるバイト列で
なければなりません(MUST)。そのためデーモンは、展開前のパスではなく
展開中にハッシュします — 分岐 F2 を参照してください。これは設計上
のものであり、穴ではありません。

### 7.3 サイズ

すべてのエントリの `size` は、マニフェストのものと等しくなければ
なりません(MUST)。2 つの独立したチェックが適切であり、デーモンは
両方を行います: 何も処理する前のセントラルディレクトリの宣言サイズ
(これは攻撃者に制御されるため、安価な嘘発見器であり、本当のチェック
ではありません)と、ストリーミング中のバイトカウントです。宣言された
サイズは、ストリーミング展開を制約するものです。ベクタ:
`size-mismatch`。

### 7.4 モード

アーカイブエントリが Unix モードを運ぶ場合、`mode & 0o777` はマニ
フェストの `mode & 0o777` と等しくなければなりません(MUST)。運ばない
場合(Windows で書かれたアーカイブ)、この比較はスキップされます; モード
の欠落は欠陥ではなく、不一致が欠陥です。マニフェストのモードは展開
ツールが適用するものです。ベクタ: `mode-mismatch`(分岐 F3 参照)。

プロデューサーは正規化します: CLI は実行可能な何か(解決されたエントリ
バイナリ、ディスク上の実行ビット、または `[bundle] executables` に
一覧されたパス)に対して `0755` を書き、それ以外には `0644` を書き
ます。これは意図的に、ディスク上の任意のモードをコピーしません: 別の
umask のもとでのチェックアウトは、そうでなければ、内容を変えずに
バンドルのバイト列を変えてしまいます。

### 7.5 ソート済み

`files` は `path` によって厳密に昇順にソートされていなければなりません
(MUST)。比較は**生のバイト列**として行われます(Unicode の照合順序で
はなく、大文字小文字を区別しません)。デーモンは厳密な昇順を強制し
(`w[0].path >= w[1].path` → 拒否)、これは重複のケースも捕捉します。
検証ツールはこの配列に対して二分探索を行ってよいことになっています;
ソートされていないものはそれを静かに間違ったものにしてしまいます。
ベクタ: `unsorted-files`。

## 8. `entry.command`

`entry.command` は、マニフェスト内で `execve` になる唯一のフィールド
です。以下のいずれかでなければなりません(MUST):

* 閉じたリスト `python`、`python3`、`node`、`bun`、`deno` と正確に
  一致する**ホストランタイム**; または
* **マニフェストが一覧するファイルへのパス。** 先頭の `./` を取り除き
  `\` を `/` に変換した後で比較します。その結果は `files[].path` に
  現れなければなりません(MUST)。

無条件に拒否されるもの:

* (トリム後に)空;
* 絶対パス(`/usr/bin/sh`、または `C:\…` のような Windows のドライブ
  文字プレフィックス);
* `..` コンポーネントを含む — ベクタ `entry-command-escape`
  (`../../../bin/sh`);
* マニフェストが一覧していないファイルを名指しする — ベクタ
  `entry-command-shell`(`sh`)。

**シェルについて。** レジストリはシェルを名前で拒否します — `sh`、
`bash`、`zsh`、`fish`、`dash`、`csh`、`ksh`、`cmd`、`cmd.exe`、
`powershell`、`powershell.exe`、`pwsh`、`pwsh.exe` — 個別のエラー
コードとともに。なぜなら `entry.command: "sh"` は制約のない `args`
を任意のコードに変えてしまうからです。CLI とデーモンは、
runtime-or-listed-file ルール(シェルはどちらでもありません)を通して
同じ判定に到達します。準拠する検証ツールは一般ルールだけを必要とし
ます; シェルを個別に名指しすることは、より良いメッセージを買うだけで
あり、異なる結果を買うわけではありません。

`entry.args` は文字列の配列で、デフォルトは `[]` です。この形式は
その内容に何の制約も課しません; ホストはそれを解釈しません。

**これを「一覧されたファイルでなければならない」に「強化」しないで
ください。** それはカタログの、スクリプト言語の半分をまるごとオフライン
にしてしまいます — すべての TypeScript と Python のプラグインはホスト
ランタイムを通して実行されます。ベクタ `ok-noarch-runtime`
(`entry.command: "node"`、`platform: any/any`)は、まさにこの間違い
を捕捉するために存在しており、これは*受理*のベクタです。

## 9. `plugin.toml` と `plugin.id`

すべてのバンドルは、他のファイルと同様に `files` に一覧された
`plugin.toml` エントリを含まなければなりません(MUST)。これはホストが
パースするプラグインマニフェストであり、その完全なフィールドリファレンス
は [マニフェストリファレンス](../reference/manifest.md) です。

2 つのルールが、バンドルがそれらを理由に拒否され得るという理由で、
*この*文書に属します:

* `MANIFEST.plugin_id` と `MANIFEST.version` は、インストーラが求め
  られていたものと、そのバンドルを提供するリスト掲載と一致しなければ
  なりません(MUST)。これがなければ、レジストリエントリ `foo` が、
  マニフェストが `bar` と言うアーカイブを提供でき、`bar` がインストール
  されてしまいます。
* **`plugin.id` はパスの一部になります** — `<plugins_dir>/<id>/` —
  ホストが作成し、書き込み、再帰的に削除するディレクトリです。その
  ため以下が検証されます:
  * 空でなく、すべての文字が `[a-z0-9-]`(小文字の ASCII 文字、数字、
    ハイフン)である;
  * ドットまたはスペースで終わってはいけません(MUST NOT)(すでに
    文字集合によって除外されていますが、後で文字集合を緩めても静か
    にこの穴が再導入されないよう、別のルールとして保持されています);
  * §6.8 の幹ルールのもとで予約された MS-DOS デバイス名であっては
    いけません(MUST NOT)。

  ベクタ: `plugin-id-traversal`、`plugin-id-con`(分岐 F4 参照)。
  `con` は Linux ではインストール可能で、Windows では不可能であり、
  実行するだけの Linux CI には見えません。

## 10. `permissions` と `permissions_hash`

`MANIFEST.permissions` は、プラグインの `[permissions]` セクションを
そのままコピーしたものです: パーミッション id をリクエストオブジェクト
(`{reason?, types?, scopes?}`)にマッピングするオブジェクトです。その
語彙と意味は [`permissions.md`](permissions.md) にあります; このセク
ションはバイト列とハッシュのみを定義します。

```
canonical_bytes  = RFC 8785 (JCS) serialisation of the permissions object
permissions_hash = "sha256:" ‖ lowercase_hex( SHA256( canonical_bytes ) )
```

ルール:

* **`null` と `{}` は同じ値です** — 何も要求しないプラグイン — どちら
  も `{}` に正規化されます。メンバーを省略するプロデューサーと空の
  オブジェクトを書くプロデューサーは、同じハッシュを生成しなければ
  なりません(MUST)。そのハッシュは
  `sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`
  = `sha256("{}")` であり、ほとんどのベクタに現れます。
* `sha256:` プレフィックスは、`files[].sha256` とは異なり、**値の
  一部です**。これがアルゴリズムを運ぶのは、この数値がリポジトリの
  境界をまたいで比較されるためです — パッカーがそれを書き、レジストリ
  が取り込み時に再導出し、ホストがそれを信じる前に再導出します。
* 空のメンバーは、空のまま発行されるのではなく**省略されます**:
  reason もなく、types もなく、scopes もないリクエストは `{}` であり、
  決して `{"reason":""}` ではありません。1 つの宣言の 2 通りの正規
  表記こそが、このハッシュが防ごうとしているズレそのものです。
* 実際の JCS: オブジェクトのキーは UTF-16 コードユニットでソートされ、
  意味のない空白はなく、文字列は RFC 8785 §3.2.2.2 が要求するとおり
  にエスケープされます。この文書の値は文字列、文字列の配列、オブジェ
  クトのみです — 数値はありません — そのため JCS の微妙な半分
  (§3.2.2 の数値正規化)はここでは問題になりません。

具体例(ベクタ `ok-permissions`、すべての実装が従うべき値):

```
{"fire_trigger":{"reason":"Fires the on_dice_roll trigger you configure"},"subscribe_events":{"reason":"Watches for command_completed"}}
→ sha256:63dde3632926bc9fb348e0973dbce01d07476a1569cede023edde451b04a6a85
```

そして引数付きで、正規化されたもの:

```
{"set_variable":{"scopes":["plugin"]},"subscribe_events":{"reason":"Watches for command_completed","types":["command_completed","tool_started"]}}
```

検証ツールは `MANIFEST.permissions` からハッシュを再計算し、自身の
`permissions_hash` と食い違うマニフェストを拒否しなければなりません
(MUST)。ベクタ: `permissions-hash-mismatch` — `permissions` ブロック
は `fire_trigger` を要求しているのに `permissions_hash` は `{}` の
ハッシュです。つまり両者は異なるプラグインを記述しています。今日誰が
これをチェックしているかは分岐 F5 を参照してください。

## 11. 旧来の `SIGNATURE` / `PUBKEY` ペア

v2 以前のバンドルは、2 つの追加エントリを運ぶことができました:
`SIGNATURE`(§3.3 の連結ダイジェストに対する 64 バイトの Ed25519 署名
の base64)と `PUBKEY`(生の 32 バイト公開鍵の base64)です。これらは
**廃止予定**であり、存在する間は:

* `files` には**決して**一覧されません(一覧されたファイルに対して
  計算されるため);
* どちらか一方が存在する場合、**両方が存在しなければならず(MUST)**、
  アーカイブ内の最後の 2 つのエントリでなければなりません(MUST)、
  `SIGNATURE` の次に `PUBKEY` の順で。それらの後に何かがあれば、
  署名がカバーする範囲の外になってしまいます。ベクタ:
  `ok-legacy-signed`(受理ベクタ — このペアは容認されますが必須では
  ありません)。
* **それらは信頼のシグナルではありません。** 自身が認証するアーカイブ
  に同梱される鍵は、誰がそれを書いたかについて何も証明しませんし、
  それらがカバーするダイジェストは曖昧なものです。検証ツールは、
  その存在、有効性、あるいは不在を、何かの証拠として扱ってはいけません
  (MUST NOT)。レジストリは警告(`W_LEGACY_SIGNATURE_ENTRY`)を発行し、
  処理を続けます。

廃止は両側でそれぞれ一度だけ名指しされているため、この 2 つがずれる
ことはありません: CLI の `LEGACY_PAIR_SUNSET`(`astra-plugin 0.5.0 /
Astra 0.4.0`)とデーモンの `LEGACY_SIGNATURE_SUNSET`(`Astra 0.4.0
(astra-plugin 0.5.0)`)です。`astra-plugin build` はすでにこれらを
書きません; `astra-plugin sign` だけがそれを行い、これはデーモンの
リーダーとともに廃止時期を迎えます。

## 12. 制限

これらの数値が宣言されている唯一の場所である
[`spec/limits.yaml`](../../../spec/limits.yaml) から:

| 制限 | 値 | 適用対象 |
|---|---|---|
| `max_archive_entries` | 10 000 | `MANIFEST.json` を含む ZIP エントリの数 |
| `max_extract_bytes` | 524 288 000(500 MiB) | 非圧縮バイトの合計 |
| マニフェストの上限 | 4 MiB | `MANIFEST.json` 単体 |

これらのいずれかを超えるバンドルは拒否されなければなりません(MUST)。
エントリ数の上限は、エントリごとに 1 レコードを割り当てる**前に**
適用し、バイト数の上限は、マニフェストが宣言する合計と、ストリーミング
中に実際に届くバイト列の両方に適用してください — 宣言された数値は
アーカイブ自身の主張です。

CLI はこれらの制限を超える*ビルド*を拒否するため、作者はユーザーの
インストール失敗からではなく、自分自身のマシン上でそれを知ります。

## 13. 検証アルゴリズム

これが実装可能な形です。検証ツールは 1 つのファイルと、任意で、リスト
掲載からの期待値 `(plugin_id, version, platform_key)` を保持します。
すべてのステップは、失敗時に**拒否**です。

**A. ファイル。**
1. `artifact_digest = SHA256(file)`。期待されるダイジェストが提供され
   一致しない場合、ここで停止します; 以下は意味を持ちません。

**B. エントリ 0、オフセット 0 から。**(§4)
2. ローカルファイルヘッダーをパースします。Name = `MANIFEST.json`;
   flags のビット 0 と 3 がクリア; method 0; size が ZIP64 センチネル
   ではなく、4 MiB 以下; マニフェストのバイト列を切り出します。
3. `manifest_digest = SHA256("astra.bundle/2" ‖ 0x00 ‖ manifest_bytes)`。
4. マニフェストを JSON としてパースします。`schema == "astra.bundle/2"`、
   正確に。

**C. セントラルディレクトリ。**(§2、§4.1、§12)
5. アーカイブを通常どおり開きます。エントリ数 ≤ 10 000。
6. セントラルディレクトリ内のエントリ 0 は `MANIFEST.json` で、格納
   されており、そのバイト列はステップ 2 のバイト列と等しい。

**D. 構造、内容より前に。**(§6、§7、§12)
7. エントリを順に走査します。それぞれについて: §6(名前ルール、
   ディレクトリなし、シンボリックリンクなし、正確な重複も大文字小文字
   を丸めた重複もなし)を適用します。
8. `Present` を構築します(3 つの予約名を除いたエントリ名)。
   `Present ⊆ Listed` と `Listed ⊆ Present` をチェックします。
9. `files` の各行について: 64 桁の小文字 16 進数 `sha256`、パース
   可能な 4 桁の 8 進数 `mode`、重複しない `path`、予約されていない
   `path`; 配列はバイト列としての `path` によって厳密に昇順。
10. `Present` 内の各エントリについて: 宣言された `size` が一致し、
    アーカイブがモードを運ぶ場合は `mode & 0o777` も一致する。
11. `files[].size` の合計 ≤ 500 MiB。
12. `SIGNATURE` または `PUBKEY` が存在する場合: 両方が存在し、
    その順序でアーカイブ内の最後の 2 つのエントリである。
13. `entry.command` が一覧されたファイルまたはホストランタイム
    である(§8)。

**E. 内容。**(§7.2)
14. `Present` 内の各エントリについて、宣言されたサイズによって
    ストリーミングされ制約された状態で: 非圧縮内容の SHA-256 が
    マニフェストのものと等しい。検証ツールが展開も行う場合は、
    書き込んだバイト列をハッシュし、2 回目の読み取りを行わない
    こと。

**F. この形式が要求し、構造的なリーダーだけでは行えない相互チェック。**
15. `permissions_hash` が `MANIFEST.permissions` からの再計算と等しい
    (§10)。
16. `plugin.toml` がパースでき、`plugin.id` が §9 に従う。
    `plugin_id` / `version` / `platform` が、バンドルを提供した
    リスト掲載(あれば)と一致する。

ステップ A–E はファイルだけを必要とします。ステップ F はファイルと
リスト掲載の両方を必要とします。

### 14.1 セルフテストの値

どの実装であっても、最も速い最初のチェックは、すべてのベクタの両方の
ダイジェストが `vectors.json` の `artifact_sha256` と
`manifest_digest` に一致することです。これらの数値は 3 つのプログラム
のどれからも来ていません:
`testdata/bundles/handcheck.sh` は、`dd`、`od`、`printf`、`cat`、
`sha256sum` から再びそれらを導出します。27 個のアーティファクト
ダイジェストと 25 個のマニフェストダイジェストが一致します — 2 つの
スキップは `manifest-not-first` と `manifest-compressed` であり、
それらのエントリ 0 は構造上、格納されたマニフェストではありません。
共有されたバグは 3 つのプログラムを互いに一致させることはできますが、
それらを coreutils と一致させることはできません。

## 15. 既知の分岐

これらは `vectors.json` の `divergence` の下にあり、それぞれが 3 つ
すべてのテストスイートによってアサートされています — コメント内の
TODO ではなく、修正されたときに色が変わるテストを伴う失敗の挙動です。
**すべての行で、この文書の判定が正しい答えです。**

| | ベクタ | 誰が足並みを外しているか | なぜそこにあるか |
|---|---|---|---|
| **F1** | `duplicate-entry-case` | デーモンだけが重複を探す前に大文字小文字を丸める | CLI とレジストリは正確一致の集合を使います。両方とも丸めるべきです。 |
| **F2** | `content-digest-mismatch` | デーモンの展開前パスがこれを受理する | **意図的です。** デーモンは展開*中*に内容をハッシュするため、ハッシュされるバイト列は書き込まれるバイト列です。これは穴ではなく、異なる瞬間での同じチェックです。 |
| **F3** | `mode-mismatch` | レジストリ bot はモードをまったく比較しません(警告のみ) | モードはレジストリではなくインストーラによって適用されるため、このチェックを格下げしました。§7.4 は比較せよと言っています。 |
| **F4** | `plugin-id-*` | CLI は `verify` でも `check` でもどちらも検証しません | デーモンの `PluginManifest::validate` とレジストリの `invalidId` はどちらも拒否します。作者自身のマシンもそうすべきです。 |
| **F5** | `permissions-hash-mismatch` | CLI のバンドルリーダーだけがハッシュを再計算しません | デーモンはインストールをブロックし(`PERMISSIONS_HASH_MISMATCH`)、レジストリは掲載を拒否します(`E_PERMISSIONS_HASH_MISMATCH`)。 |

これらのどれかを閉じたら、`divergence` ブロックを削除し、その実装の
`expect` を判定に設定してください — その瞬間、テストスイートがあなた
に教えてくれます。

## 16. 検証済みバンドルが教えてくれること、教えてくれないこと

**教えてくれること:** このバイト列は、それを一覧するマニフェストが
持つ正確なバイト列であり、アーカイブ内のすべてのファイルは両方向で
説明され、インストールディレクトリの外に何も展開されず、あなたが
持っているダイジェストは、他の誰かがこのファイルに対してそれを計算
しても得られるダイジェストと同じです。

**教えてくれないこと:** 誰がそれを書いたか(それは証明と署名済み
インデックスの役目です — [`registry-index.md`](registry-index.md))、
それが現在撤回されているかどうか(それは失効リストの役目です)、
実行時に何を呼び出せるか([`permissions.md`](permissions.md))、
起動後にそのプロセスがマシンに対して何ができるか。プラグインはユーザー
として、ユーザーの権限で実行されます。この形式のどの部分もそれを
変えず、Astra の UI のどの部分もそれを変えるとほのめかしてはいけません。

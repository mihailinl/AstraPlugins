# パーミッション — 規範仕様

**ステータス:** 規範的。語彙、ゲート、上限、4 つの出所経路、そして
ハッシュは、すべて実装され強制されています; 何かが仕様化されているが
まだ強制されていない場合、この文書はその行でそう述べます。

要求語は RFC 2119 に従います。

`plugin.toml` には 2 つの直交するセクションが存在し、それらを混同する
ことが、この語彙が修正するために作られたバグです:

| セクション | 方向 | 問い |
|---|---|---|
| `[capabilities]` | デーモン → プラグイン | *私は何を実装しており、Astra はそれに何を呼び込めるか?* |
| `[permissions]` | プラグイン → デーモン | *私は何を呼び出せて、どんなサーフェスを渡され得るか?* |

これらはかつて 2 つのものに対する 1 つの単語であり、その単語は最初の
意味を指していました — これが、`dom_access` が、宣言するだけでプラグ
インが自分自身に付与できるケーパビリティになってしまった経緯です。

---

## 1. 語彙

8 つの id、閉じた集合です(`astra-plugin-manifest/src/permissions.rs`、
`PERMISSION_NAMES`、テストによって enum に固定されています)。レジス
トリは、リスト掲載の id をこのリストに対して検証し、Astra のローカライズ
されたラベルテーブルもこれをキーとしているため、ある場所には追加され
他の場所には追加されなかった id は空白の行として描画されます。

| id | ゲートする対象 | 何を許可するか | 高リスク |
|---|---|---|---|
| `fire_trigger` | `PluginHostService.FireTrigger` | ユーザーが保存した自動化を実行する | |
| `subscribe_events` | `SubscribeEvents` | デーモンイベントを受信する。**宣言された種別に制限される**(§1.1) | |
| `set_variable` | `SetVariable` | デーモンの変数コンテキストに、呼び出したプラグインの名前空間で書き込む | |
| `send_chat_message` | `SendChatMessage` | AI のターンを駆動する — ユーザーのトークンを消費し、そのアシスタントの声で話す | ● |
| `push_to_ui` | `PushToUi` | Astra ウィンドウにイベントを push する | ● |
| `set_theme_contribution` | `SetThemeContribution` | アプリ全体のスタイルを変更する | ● |
| `dom_access` | *RPC なし* — **サーフェス** | ユーザーの会話とすべての他プラグインのインターフェースへのアクセスを伴い、Astra ウィンドウ内でプラグイン自身のスクリプトを実行する | ● |
| `client` | *RPC なし* — **サーフェス** | クライアントフロントエンドとして振る舞う: 独自のチャットサーフェス、独自のセッション | ● |

**●が付いた 5 つは高リスク**(`HIGH_RISK_PERMISSIONS`)であり、それぞれ
が独自の同意チェックボックスを得ます。計画の §4.3 は 4 つのチェック
ボックスを詳述し `push_to_ui` を省略していますが、§5.6 は 5 つを一覧
します。実装は**和集合**を取ります。なぜなら、この不一致は UI の段落と
セキュリティのセクションの間のものであり、チェックボックスが多すぎる
ことのコストはクリック 1 回ですが、少なすぎることのコストはその性質
そのものだからです。

**`dom_access` と `client` はどの RPC もゲートしません**。これがまさに
これらに 2 つ目の強制ポイントが必要な理由です: これらは、呼び出しが
応答される場所ではなく、*サーフェス*が渡される場所(§4.2)で強制され
ます。

### 1.1 パーミッションの引数

`[permissions]` のエントリは真偽値ではなくオブジェクトです:

```toml
[permissions]
fire_trigger     = { reason = "Fires the on_dice_roll trigger you configure" }
subscribe_events = { types = ["command_completed"], reason = "Reacts when a command finishes" }
set_variable     = { scopes = ["plugin"] }
```

| メンバー | 型 | 意味 |
|---|---|---|
| `reason` | string、140 文字以下 | 作者自身の言葉(§6) |
| `types` | array of string | **`subscribe_events` のみ。** イベント種別の許可リスト |
| `scopes` | array of string | **`set_variable` のみ。** `plugin` / `session` / `persistent`。**予約済み** — デーモンは今日、すべてのプラグインの書き込みをプラグイン id で名前空間分けしているため、これはまだ何も絞り込みません。これがパースされるのは、これを宣言するマニフェストが公開可能であり、どこでも同一にハッシュされるようにするためです |

**`subscribe_events.types` は、デーモンがイベントごとに強制する許可
リストであり、空のものは何も許可しません。** 3 つの状態があり、真ん中
の状態こそがポイント全体です:

* パーミッションが存在しない → ストリームはまったくなし;
* パーミッションは保持されているが `types` が空 → **何も許可しない**;
  デーモンは、永遠に沈黙するストリームを返す代わりに、修正方法を名指
  ししたメッセージとともに購読を拒否します;
* `types` が一覧されている → 正確にそれらの
  `AstraEvent::event_type_str()` の値。

直感的な読み方 — 「フィルタなしはすべてを意味する」 — こそ、この
パーミッションが閉じるために存在する穴です: フィルタなしの購読者は、
ユーザーが言うすべての言葉である `speech_recognized` を受信して
しまいます。

### 1.2 未知の id は保持され、拒否されません

このビルドが一度も聞いたことのない id を名指しするマニフェストは
**受け入れられます**。理由は 2 つあり、どちらも同じ方向を指しています:

1. **前方互換性。** 新しい id は新しい Astra とともに出荷されます。
   未知の id を拒否するデーモンは、すべての追加をすべての古いデーモン
   にとってのフラグデーになってしまいます。
2. **ハッシュ。** `permissions_hash`(§5)は、3 つの実装によってこれ
   らのバイト列に対して計算されます。リーダーが認識しなかったキーを
   落とすと、そのうちの 2 つが何に署名されたかについて食い違って
   しまいます。

未知の id は**無効**です — デフォルト拒否とは、決して何も許可しない
ことを意味します — そしてこれは黙って行われるわけではありません。
同意シートは、それを落とすのではなく、`permission.unrecognised` ラベル
を通してそれを描画するため、ユーザーには、プラグインがこのバージョンの
Astra が知らない何かを要求していることが伝えられます。
`Permissions::unknown()` は、ツールがそれらを列挙できるように存在
しますが、**`astra-plugin check` は今日それを行いません** — `[permissions]`
セクションが存在すると報告し、そこで止まります。

(対照的に `[capabilities]` は `deny_unknown_fields` です: これは
タイポが `false` とまったく同じように読める、真偽値の閉じた集合です。)

## 2. デフォルト拒否、そして何も必要としない 4 つの RPC

**`[permissions]` セクションが存在しないことは、常に許可される集合を
超えるホスト RPC が付与されないことを意味します。** セクションの欠落は
「未指定」ではありません; それは完全な答えであり、その答えは「いいえ」
です。

常に許可される集合は 4 つであり、2 つのカナリアがすべての RPC をそれに
対してチェックするテーブル(`host_service.rs` の
`HOST_RPC_PERMISSIONS`)として書き記されているため、ゲートされていない
新しい RPC は静かな見落としではなくテスト失敗になります:

| RPC | パーミッション |
|---|---|
| `Register` | — |
| `PluginLog` | — |
| `GetPluginSelfConfig` | — |
| `GetDaemonInfo` | — |
| `SubscribeEvents` | `subscribe_events` |
| `SendChatMessage` | `send_chat_message` |
| `FireTrigger` | `fire_trigger` |
| `SetVariable` | `set_variable` |
| `SetThemeContribution` | `set_theme_contribution` |
| `PushToUi` | `push_to_ui` |

`GetDaemonInfo` は、計画の 3 つのリストへの 1 つの追加であり、見落とし
ではなく意思決定です: これは `version`、`state`、`grpc_port`、
`language` を返しますが、これらすべては `PluginRegisterResponse` が
すでに呼び出し元に渡しているものであり、新しいものは何も開示しません。
これに対してパーミッション id を発明することは、何も守らないチェック
ボックスをユーザーの前に置くことになり、何も守らないチェックボックス
こそが、ユーザーがチェックボックスにチェックを入れることを学習する
原因です。

**`client_session_token` はすべてのプラグインに発行されます。** この
トークンは*認証*(誰が呼び出しているか)であり、*認可*(その人が何を
してよいか)ではありません。`client` でないプラグインからこれを差し
控えることは、常に許可される集合である `PluginLog`、
`GetPluginSelfConfig`、`SubscribeEvents`、`FireTrigger` を拒否する
ことになり、すべてのプラグインと両方のインツリーのサイドカーを壊して
しまいます。`client` のゲートは、トークンではなく、上限と特定のサーフェス
に属します。

## 3. 宣言することは求めることであり、付与は別のオブジェクトです

**`plugin.toml` の中の何も付与ではありません。** `[permissions]` ブロック
は作者の*申請*です。**許可された集合**は、デーモンが出所経路ごとに解決
し、プラグインが到達できない場所に保存する別のオブジェクトです —
`<base_dir>/registry/records/<id>.json`、プラグインツリーの兄弟であり
決してその子ではなく、デーモンが保持する鍵で MAC されています。

強制はこの許可された集合を読むのであって、マニフェストを読むことは
決してありません — 各ゲートされた RPC の先頭にある呼び出しの形
(`host_service.rs` からの説明的な抜粋であり、実行可能なサンプルでは
ありません):

```rust
let (plugin_id, grants) =
    self.require_permission(&request, Permission::FireTrigger, "FireTrigger").await?;
```

自分のマニフェストを編集することで自分の付与を広げられるプラグインは、
パーミッションシステムが単なるコメントであることを意味します。これは
フェーズ 4 以前は文字どおり真実でした: `[capabilities] dom_access =
true` — プラグイン自身のディレクトリ内のファイルの 1 行 — が、
レンダラーがプラグインのスクリプトを Astra ウィンドウ自体にロードする
ことで尊重する UI コントリビューションに、そのままコピーされていました。

**なぜレコードがプラグインのディレクトリにないか。** プラグインは
ユーザーとして、インストールディレクトリに設定された `current_dir` で
動きます。モード 0600 は他のユーザーからは守りますが、当の本人からは
守りません。当の本人が書き込めるレコードは、悪意のあるプラグインが
自分自身に `dom_access` を付与し、TOFU ピンを上書きし、ダイジェスト
キーによる失効を回避するために `artifact_sha256` を書き換え、開始時の
再チェックが通るようにファイルごとのハッシュを書き換えることを許して
しまいます。

### 3.1 ケーパビリティブリッジ

`dom_access` と `client` は `[capabilities]` の真偽値**であり**、かつ
パーミッション id です。分割より前に書かれたすべてのプラグインは、
古い場所で欲しいものを述べています — `companion`、`doom`、
`bad-apple` を含め、これらはどれも `[permissions]` セクションをまったく
宣言していません。

そのため `[capabilities] dom_access = true` というビットは、
`[permissions]` のエントリとまったく同じように**申請**として読まれ、
同じテーブル(`declared_permissions()`)から正確に同じ答えを得ます。
このブリッジは意図的に「ケーパビリティのビットがパーミッションを付与
する」というものでは*ありません*: これは申請が存在する場所にそのビット
を置くことで、「これはしてよいか?」に対する答えを 1 つにし、2 つに
しません。

作者への帰結: **レジストリを通して公開されるプラグインは
`[permissions] dom_access` を宣言しなければなりません**。なぜなら、
レジストリインストールはその信頼レコードから付与しますが、それは
バンドルの `MANIFEST.json` の `[permissions]` ブロックから書かれる
ものであり — そしてそのエントリこそが、同意シートが描画し、ユーザーが
チェックするものだからです。

## 4. 許可された集合はどこから来るか

### 4.1 4 つの出所経路

`decide_grants()` は、この表を 1 つの純粋関数にしたものです。

| 経路 | 許可される集合 |
|---|---|
| **組み込みサイドカー**(`builtin_stt`、`builtin_vox`) | そのサイドカーの `build_manifest()` の隣にある**コードで宣言された**集合。信頼レコードなし、ディスク読み取りなし — サイドカーは*設計上*レコードを持ちません。それを探すコードパスは、それがないと失敗し得るコードパスになってしまうからです |
| **レジストリインストール** | インストール時に書かれた信頼レコード: バンドルの `MANIFEST.permissions`、同意チェックの後、そのティアの上限でキャップされたもの |
| **`ImportPluginFile`**(帯域外からの `.astraplugin`) | `tier: "local-unverified"` の信頼レコード — マニフェストが宣言した集合が**ティア 2 の上限でキャップされる** |
| **サイドロード**(ソースディレクトリ、開発者モード) | `tier: "sideloaded"` の信頼レコード — マニフェストが宣言した集合、**上限なし** |

その表にない、しかし同様に規範的な 4 つの分岐:

| 状態 | 許可されるもの |
|---|---|
| `Untrusted` — レコードが期待されていたが信用できない | **何もなし** |
| `TamperDetected` — ファイルが記録されたダイジェストとすでに一致しない | **何もなし** |
| `Revoked` — 署名済みの撤回リストがこれをカバーする | **何もなし** |
| `Unrecorded` — 信頼レコードが存在する前にインストールされた、レコードがまったくない | マニフェストが宣言した集合、**ティア 2 の上限でキャップされる** |

`Untrusted` は手動でなお起動できますが、その場合は付与なしで動作
します: 「ユーザーが求めた」はバイト列についての証拠ではありません。
`Unrecorded` が拒否ではなくキャップされるのは、それらのプラグインに
何も付与しないことがアップグレード時に動作しているインストールを、
ユーザーが直す手段もなく壊してしまうためであり、それらにマニフェスト
を上限なしで付与することは、それらのいずれもが自分のディレクトリ内の
ファイルを編集することで `dom_access` を自己付与できるようにしてしまう
ためです。ティア 2 の上限は、まさに「どこかから来たが、何も証明して
いない」という形そのものです。

信用できるレコードを持たない `Verified` プラグインは**何も**得ません:
`Verified` は信用できるレコードを*意味し*、その不可能な組み合わせへの
答えはマニフェストにフォールバックすることではありません。

すべての拒否はその出所を名指しします(`GrantSource::describe`) —
「拒否されました」とだけ言って「そしてこれがそれについて何も語らな
かった出所です」と言わないことが、パーミッションシステムが差し戻される
失敗パターンです。

### 4.2 2 つのゲート、1 つではなく

パーミッションは、**両方**が成り立つときにのみ尊重されます:

1. **付与(grant)** — 同意シートが生み出し、信頼レコードが保持する
   インストールごとの答え;
2. **上限(ceiling)** — どんなレコードも買い越せない出所ごとのルール。

`require_permission` は、パーミッションをゲートする 6 つのホスト RPC
— `SubscribeEvents`、`SendChatMessage`、`FireTrigger`、
`SetVariable`、`SetThemeContribution`、`PushToUi` — に対して 1 つ目
を尋ねます。残りの 4 つ(`Register`、`GetPluginSelfConfig`、
`PluginLog`、`GetDaemonInfo`)は `HOST_RPC_PERMISSIONS` の中で `None`
を運び、常に許可されます; §2 に表と理由があります。
`ceiling_admits` は、*サーフェス*が渡されるあらゆる場所 —
`PluginStatusMsg`、UI コントリビューションのレスポンス、アクティブ
テーマのレスポンス — で 2 つ目を尋ねます。そのためレンダラーが尊重
してしまうかもしれない値を受け取ることは決してありません。付与マップ
に見当たらないプラグインは拒否されます: 「それについて何も解決しな
かった」は、システム内で最もリスクの高いサーフェスをそれに提供する
理由にはなりません。

## 5. ティアの上限

| ティア | 出所 | 上限 |
|---|---|---|
| **1 · レジストリ** | インストールアルゴリズムに従って検証済み | **すべて**、同意を条件として。失敗時のオーバーライドはない |
| **2 · ローカルファイル**(`ImportPluginFile`) | 帯域外で受け取った `.astraplugin` | `send_chat_message`、`set_theme_contribution`、`dom_access`、`client` は**警告ではなく無条件で拒否される** |
| **3 · サイドロード** | ユーザーがファイルダイアログで指し示したソースディレクトリ、開発者モード有効 | **なし** — そして**決して自動起動しない**: 開発者モードはロード時に必要であり、再起動するとユーザーが再度起動するまで停止したままになる |

サイドロードのティアは、来歴パネル内の `provenance.tier.sideloaded`
(「フォルダから読み込まれた」)としてユーザーに表面化されます。計画
はまた、`dom_access` が有効な場合にカードとウィンドウの chrome 上に
恒久的で消せない「DEVELOPER — unverified code from a local
directory」バッジを求めています; **そのバッジは今日 UI にはありません**
し、この文書はそれを主張しません。

**ティア 2 の昇格は実装されていません。** 計画は、そのダイジェストが
新しいインデックスに現れ、バージョンの下限が保たれるとき、インポート
されたファイルをティア 1 に昇格させることを記述しています; 今日、
`import_plugin_file` はインストール経路に検証済みリリースを一切渡さ
ないため、インポートされたバンドルは、そのダイジェストについてインデ
ックスが何と言おうと、**常に** `local-unverified` です。公開すれば、
誰かにメールで送ったファイルの上限が遡って解除されると作者に伝えないで
ください。

ティア 2 の拒否リストは `TIER2_REFUSED_PERMISSIONS` です — 意図的に
`HIGH_RISK_PERMISSIONS` と**同じリストではありません**: `push_to_ui`
はチェックボックスに値するものの、ユーザーが選んでインポートしたファイル
を拒否するには値しません。この 4 つは §5.5 から引用されたものであり、
推測されたものではありません。

**ティア 3 はティア 2 に素敵なバッジを付けたものではありません。** この
分割は*検証状態*ではなく*意図*によるものです。自分のディスク上の
ディレクトリにファイルダイアログを向けたユーザーは、他所から届いた
未検証ファイルよりも強いシグナルを与えています — そしてこのプロジェクト
自身の看板サンプルである `companion`、`doom`、`bad-apple` はすべて、
ティア 2 が拒否する DOM 経路を必要とします。ティア 3 に上限を設けると、
`astra-plugin dev` は不可能になってしまいます。

未知の id はどの上限によっても落とされます(`capped()` は
`Permission::from_id(id).is_some_and(keep)` でフィルタします): 分類
できなかった id を通してしまう上限は、次のリリースの形をした穴を持つ
上限でしょう。

**あらゆる場所で守られている設計ルール:** *ユーザーのオーバーライド
が買えるものは、Astra が精査していないソースからのコードを実行する
権利だけです。それは決して、検証済みプラグインが求めなければならな
かったであろうパーミッションを買うことはできません。*

## 6. 同意

同意シートは、レジストリが取り込み時にバンドルの `MANIFEST.json` から
コピーした、カタログレコードの `permissions` から、**ダウンロードの前
に**描画されます。

* 各 id は**Astra 自身のローカライズされたラベルテーブル**を通して
  描画されます。作者の `reason` は従属的です: 引用符付き、プレーン
  テキスト、140 文字以下、常に*「The author says:」*というプレフィックス
  付きです。これは決してラベル自体では**ありません** — 文言の修正は
  Astra とともに出荷され、リスト掲載によって作成可能であってはいけません。
* 各高リスクパーミッションは**独自のチェックボックス**を得ます;
  `dom_access` は 2 つ目の画面を得ます。
* この答えは、**申請ではなく上限として**インストールに渡されます
  (`InstallOptions::consent`): *バンドル*がシートに表示されなかった
  何かを要求する場合、インストールは `PERMISSIONS_NOT_CONSENTED` で
  拒否されます。2 つのリストは異なる場所から来ています — シートは
  カタログレコードを描画し、信頼レコードはバンドル自身のマニフェスト
  から付与します — そしてそれ以外に両者を一致させるものは何もありません。
  何も宣言しないリスト掲載が `dom_access` を要求するバンドルを出荷する
  ことは、同意画面をまさに狙った「悪意のあるレジストリ」のケースです。
* `consent: None` — 単項インストール、インポート、テスト、採用 — は
  同意前の挙動を保持します: バンドルの宣言された集合を付与し、ティア
  でキャップします。

**更新。** インストール済みバージョンに許可されていなかったパーミッション
を要求するバージョンは `PERMISSIONS_WIDENED` で拒否され、レビュープロン
プトになります; ユーザーの明示的な承認がそれをインストールに変える
ものです。比較は**パーミッション名によるものであり、リクエストオブジェ
クト全体によるものでは決してありません**: `reason` の文言を改善した
作者は何も広げておらず、それを拡大とみなす更新ゲートは、唯一重要な
ダイアログをユーザーにクリックし通す訓練をさせてしまいます。

**撤回は即座に発効します。** `granted_permissions` への何らかの変更、
同意の撤回、失効のいずれについても、デーモンはサーバー側の購読を
落とし、セッショントークンを無効化するため、動いているイベントストリーム
が絞り込みを生き延びることはありません。プラグインには、どれが起きたか
が `x-astra-teardown-reason` トレーラー(`grants_changed`、
`consent_declined`、`revoked`、`trust_lost`、`disabled`、
`uninstalled`、`re_registered`)を通して伝えられます — 安定したトークン
であるため、SDK は再試行が無駄かどうかを知るために英語をパースする
必要が決してありません。

### 6.1 良い `reason` を書く

これは判断しようとしているユーザーに表示されます。140 文字以下で
なければならず(MUST)、以下であるべきです(SHOULD):

* API ではなく**ユーザーが認識できる機能を名指しする** — 「calls
  FireTrigger」ではなく「Fires the on_dice_roll trigger you
  configure」;
* 常にではない場合は**いつなのかを言う** — 「only while a recording
  is in progress」;
* パーミッション自身のラベルを繰り返すことを避ける; Astra がすでに
  それを描画しています;
* 緊急性、脅し、ユーザーへの指示を避ける。ジェネレータは、それがそのまま
  表示されるあらゆる場所で、bidi オーバーライドやゼロ幅接合子を含む
  テキストを拒否し、同意シートは例外を作るのに最も適さない場所です。

もっともらしい理由のないパーミッションは、マニフェストから削除すべき
パーミッションです — これを自動でチェックするものは何もなく、リスト
掲載を読むレビュアーだけが唯一の防波堤です。

## 7. `permissions_hash`

```
permissions_hash = "sha256:" ‖ lowercase_hex( SHA256( JCS(permissions) ) )
```

* `JCS` は RFC 8785 の正準 JSON です — キーは UTF-16 コードユニットで
  ソートされ、コンパクトです。両方のリポジトリが実装しているプロファイル
  については
  [`registry-index.md` §3](registry-index.md#3-正規化jcs-プロファイル)
  を参照してください。
* **`null` と `{}` は同じ値**であり同じにハッシュされるため、メンバー
  を省略するプロデューサーと空のオブジェクトを書くプロデューサーは
  一致します:
  `sha256:44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`。
* **空のメンバーは、空のまま発行されるのではなく省略されます。**
  `set_variable = {}` は `{}` であり、決して `{"reason":""}` では
  ありません。1 つの宣言の 2 通りの正規表記こそが、このハッシュが防ご
  うとしているズレそのものです。
* `sha256:` プレフィックスは値の一部です。なぜならこれはリポジトリの
  境界をまたぐからです。

3 つの実装がこれを計算し、3 つすべてが比較されます:
`astra-plugin` のパッカーはそれを `MANIFEST.json` に書きます; レジス
トリ bot は取り込み時にそれを再導出し、食い違いをリスト掲載しません
(`E_PERMISSIONS_HASH_MISMATCH`); デーモンはマニフェストを信じる前に
それを再導出し、インストールをブロックします
(`PERMISSIONS_HASH_MISMATCH`)。ゴールデンベクタ: `ok-permissions`
(正しい非空マップ)と `permissions-hash-mismatch` — [`bundle-v2.md`
§10](bundle-v2.md#10-permissions-と-permissions_hash) と、CLI の
リーダー単独に固有な F5 の分岐を参照してください。

このハッシュは信頼レコードにも記録され、発見時に再チェックされるため、
インストール後にその場で編集された `plugin.toml` は、従われるのでは
なく検出されます。

## 8. パーミッションが何ではないか

`[permissions]` は*デーモンがプラグインのために何をするか*に答えます。
*そのプロセスがマシンに対して何ができるか*には答えません。

プラグインは、デーモンによって起動される、ユーザーとしてそのフル権限
で動くネイティブプロセスです。ユーザーのファイルを読み、ソケットを
開き — 今日では — デーモン自身のトークンをディスクから読むことがで
きます。**サンドボックスはありません。** 隔離(Landlock/seccomp、
Windows での AppContainer または low-integrity トークン、rlimits)は
将来の作業として範囲づけられており、明示的にこのリリースには含まれて
いません。

この文書がすべての消費者に守らせている 2 つの帰結:

* **Astra の UI はサンドボックスを決してほのめかしてはいけません。**
  来歴パネルの「証明しない」ブロックと、同意シートの一文は、まさに
  この理由のために存在します。
* **パーミッション拒否は、デーモン自身の権限 — 自動化、チャットの
  ターン、テーマ、ウィンドウ — に対してのみ、実在する境界です。** それ
  以外のすべてに対しては、監獄ではなく、トリップワイヤーです。

ここで正直であることは、末尾に取ってつけた但し書きではありません。
サンドボックスとして説明されるパーミッションモデルは、そのユーザーが、
モデルがまったくない場合よりも悪い決定を下すことになるパーミッション
モデルです。

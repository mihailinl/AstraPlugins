# セキュリティモデル

何かを公開する前に、そして何かをインストールする前に、これを読んでください。

## 1 文で言うと

**プラグインは、あなたのフルユーザーアカウントの権限で動くネイティブ
プロセスです。** あなたのファイルを読み、ソケットを開き、プログラムを spawn
できます。Astra にはこれをサンドボックス化したり、隔離したり、OS レベルで
制限したりする仕組みは一切ありません。

これはこのページがごまかしている抜け穴ではなく、現状の設計そのものです。
隔離は本番計画の**フェーズ 7** であり、それが省略ではなく意思決定である
ことを示すためにそこに名付けられていますが、**実装されていません**。
実現する場合の候補作業: Linux での Landlock + seccomp、Windows での
low-integrity トークンまたは AppContainer、rlimits。それまでは、
「署名済み」も「掲載済み」も、そのプロセスがあなたのマシンに対して何が
できるかについては何も語りません。

Astra がそうではないとほのめかしかねない箇所では、必ずこれを声に出して
言うことが*要求されます* — インストール同意シートと来歴パネルはどちらも、
証明はコードが安全であることを証明するものではないと述べる恒久的なブロック
を持っています。デーモンはすでに、未検証のインストールを拒否する際の
メッセージでこう言っています: 「プラグインはあなたのフル権限を持つ
ネイティブプロセスとして動作するため、未検証のものはあなたのマシンを
乗っ取る可能性があります」(`astra-daemon/src/plugins/manager.rs`)。
アプリ自身の画面がどう見えるかは Astra が文書化すべきことであり、この
リポジトリの仕事ではありません。このページはデーモン、CLI、フォーマット
について説明します。

## 各仕組みが実際に答えていること

4 つの層、4 つの異なる問い。これらを混同することが、「署名されている」が
「安全である」に変わってしまう経緯です。

| 層 | 仕組み | 誰が検証するか | 答える内容 |
|---|---|---|---|
| 1. ビルドの来歴 | GitHub アーティファクト証明(Sigstore keyless、OIDC) | CI 内のレジストリ bot | 「このバイト列はリポジトリ R のコミット C にあるワークフロー W から来た」 |
| 2. 配布の信頼 | 署名済みインデックス内の、アーティファクトのダイジェストに対する Ed25519 副署名 | デーモン、オフラインで | 「Astra はまさにこのバイト列を掲載しており、撤回されていない」 |
| 3. 継続する同一性 | `github:owner/repo` の TOFU(初回信頼)ピン | デーモン、オフラインで | 「この更新は、インストール時と同じ作者からのものである」 |
| 4. 実行時の権限 | すべてのホスト RPC における `[permissions]` + `require_permission` | デーモン、呼び出しのたびに | 「このプラグインが Astra に依頼してよいことは何か」 |

どれも「このコードは安全か」には答えません。その問いには機械的な答えは
なく、答えられるかのようにほのめかすシステムは、答えられないと認める
システムより悪いものです。

## 今日真実であり、これからも和らげられないこと 2 つ

### 信頼チェーンは仕様化・実装されているが、1 リンク分だけ届いていない

ルートキーは存在し、その下の委譲も今では存在します。**存在しないのは
カタログ自身の署名**であり、そのためユーザーのマシン上では何も検証されません。
具体的には([`spec/registry-index.md` §0.1](../spec/registry-index.md)):

- レジストリの `root.json` は `"status": "provisioned"` と、2026-08-11 に
  オフラインの儀式で生成された 2 つの Ed25519 キーを持っています。
- デーモンの `PRODUCTION_ROOT_KEYS` は同じ 2 つを列挙しています —
  このファイルが存在するのは、第三者がバイナリを逆アセンブルすることなく
  これらを読めるようにするためであり、両者の不一致が可視化されるように
  するためです。
- ルートキーはカタログに署名しません。`trust.json` に署名し、それが
  インデックス署名キーに委譲します。**その文書は今では署名されています。**
  `registry/v1/trust.json` は `astra-root-2026a` の下で検証され、
  `astra-index-2026a` に委譲し、レジストリの bot がビルド証明として
  受け入れる単一の再利用可能ワークフローのコミットを名指ししています。
  レジストリ自身の `node tools/sign-trust.mjs --verify
  registry/v1/trust.json` がそのすべてを出力します。そのため、取り込み
  側のブロック `E_TRUST_UNPROVISIONED` はもう発生しません。
- **しかし `registry/v1/index.json` は今も `"signatures": []` を
  持っており**、`revocations.json` も同様です。カタログに署名がない
  ため、委譲されたキーがチェックできるものが何もなく、すべてのカタログは
  依然として `UNSIGNED` に分類されます。ただし理由は `NoTrustAnchor` では
  なく **`NoSignatures`** です: アンカーは届いたが署名が届いていない、と
  いう意味です。`NoTrustAnchor` はより古く、より悪い状態で、検証済みの
  `trust.json` がそもそもビルドに届いていないことを意味します。
- そして撤回リストは厳密に検証されるため、未署名の撤回リストは拒否され、
  そのため **失効の強制もまだ機能していません**。

したがって、デフォルトのビルドは今もフェイルクローズします。ここには、
今日あなたが手にしている保証についての約束は何もありません。この仕組みが
ユーザーにとって意味を持ち始めるのは、署名済みインデックスが存在するように
なってからであり、それより前ではありません。

### ローカルの署名鍵は一切の信頼を与えません

`astra-plugin keygen` と `astra-plugin sign` は存在します。これらは
任意の第 2 要素です — GitHub アカウントの乗っ取りに対する多層防御であり、
その価値は、鍵が盗まれた GitHub セッションが存在しない場所にあることに
あります。

これらは Astra にプラグインをインストールさせる要因では**ありません**。
自分の鍵で署名したバンドルは、未署名のものとまったく同じように信用され
ません。デーモンは ZIP 内の `SIGNATURE`/`PUBKEY` ペアを *固定された Astra
発行者鍵* に対して検証するのであって、アーカイブ内の鍵に対してではあり
ません。`astra-plugin build` は実行するたびにそれを述べます。

<!-- doctest: output from="astra-plugin build ." -->
```
  Unsigned. Local keys are not a trust signal in Astra — trust comes from the registry.
```

そして `astra-plugin sign` は成功時にそれを述べます。意図的に `--help`
に埋もれさせていません。

<!-- doctest: output from="astra-plugin sign <bundle>" -->
```
This signature is an optional second factor, not a trust signal.

Astra does not verify it against your key — the daemon checks the in-ZIP pair against a
pinned Astra publisher key, so a bundle signed with your own key is untrusted by
construction, exactly as an unsigned one is.
```

ZIP 内のペアは廃止予定のフォーマット機能です。このコマンドとそれが
書き込むエントリの両方が、削除のスケジュールに載っています。

`astra-plugin login` は存在せず、今後も存在しません。公開はリポジトリと
タグを運ぶものであり、保存すべき資格情報も、漏洩し得る資格情報もない
からです。

## パーミッションゲートが行うこと

デーモンは `[permissions]` を 1 か所で強制します: `require_permission`、
`PluginHostService` の 10 個の RPC のうち 6 個に対してです。残りの 4 つ
— `Register`、`GetPluginSelfConfig`、`PluginLog`、`GetDaemonInfo` — は
**常に許可されており**、パーミッションチェックは一切実行されません。
これらはデーモンの `HOST_RPC_PERMISSIONS` テーブルでは `(…, None)` で
あり、その本体には `require_permission` の呼び出しがありません。空の
`[permissions]` ブロックを持つ登録済みプラグインは、この 4 つに到達でき、
それ以外には到達できません。なぜこれらが無償なのかは
[パーミッションのリファレンス](../3-reference/permissions.md#何も必要としない-4-つの呼び出し)
にあります。`require_permission` が参照するテーブル — デーモン内の
`HOST_RPC_PERMISSIONS` — はパリティルール R6 によって
[`spec/hooks.yaml`](../../../spec/hooks.yaml) に固定されているため、
生成された[パーミッション列](../reference/parity.md)がそれを強制する
コードからずれることはあり得ません。

2 つの独立したゲートがあり、両方を通過する必要があります
([`spec/permissions.md` §4.2](../spec/permissions.md))。

1. **付与(grant)** — 同意シートによって生み出され、信頼レコードが保持する、
   インストールごとの答え;
2. **上限(ceiling)** — どんなレコードも買い越せない、来歴ごとのルール。

マニフェストは*申請*です。ティア 1 と 2 では、許可された集合はプラグイン
が書き込めない場所に置かれます。なぜなら、自分のマニフェストを編集する
ことで自分の許可を広げられるプラグインは、パーミッションシステムが単なる
コメントでしかないことを意味するからです。

**ティア 3 は例外であり、意図的なものです。** サイドロードされたソース
ディレクトリについては、デーモンの `decide_grants` は
`declared.capped(|_| true)` を返します — マニフェストそのものが同意記録
であり、読み込みのたびにプラグイン自身のディレクトリから読まれ、その上に
上限はありません。したがってサイドロードされたプラグインは、再起動の間に
自分の `plugin.toml` を編集することで、語彙全体に至るまで自分のパーミッション
を広げることができます。これが、開発者モードが開発者向けツールであり
インストール経路ではない、もう 1 つの理由です。

5 つのパーミッションは高リスクであり、それぞれが独自の同意チェックボックス
を持ちます: `send_chat_message`、`push_to_ui`、`set_theme_contribution`、
`dom_access`、`client`。`dom_access` にはさらにもう 1 画面あります。
読む価値のある `reason` の書き方を含む詳細:
[パーミッション](../3-reference/permissions.md)。

## プラグインの出所がその上限を決める

| ティア | 出所 | 上限 |
|---|---|---|
| **1 · レジストリ** | ストアからインストール、検証済み | 要求したすべて。ただし同意が必要。検証失敗をオーバーライドする手段はない |
| **2 · ローカルファイル** | 手動でインポートされた `.astraplugin` | `send_chat_message`、`set_theme_contribution`、`dom_access`、`client` は**警告ではなく、無条件で拒否されます** |
| **3 · サイドロード** | ソースディレクトリ、開発者モード有効 | **上限なし** — そして自動起動は決してしない |

ティア 3 が上限なしなのは意図的です: これは UI プラグインの作成ループであり、
上限を設けると `dom_access` を開発できなくなってしまいます。これは明示的な
設定の背後にゲートされており、再起動後に自動的に開始することは決してなく、
インストール手段としてではなく
[開発者向けツールとして文書化されています](../5-publish/sideload.md)。

マニフェストが何と言おうと、4 つの状態は**何も得られません**:
`Untrusted`、`TamperDetected`、`Revoked`、そしてレコードを信用できない
`Verified` プラグインです。信頼レコードが存在する前にインストールされた
プラグイン(`Unrecorded`)は、マニフェストがティア 2 の上限にキャップ
されます — 「どこかから来たが、何も証明していない」というのはまさに
その形です。

## 防御されていないこと

読者に発見させるのではなく、名指しします。

| 脅威 | 状態 |
|---|---|
| プラグインがあなたのファイル、鍵、ネットワークを読むこと | **防御されていません。** 隔離の仕組みは存在しません — フェーズ 7 |
| プラグインが `daemon.token` を読み取り、クライアントとして登録すること | **防御されていません。** 同じ理由です |
| 悪意のある、あるいは侵害されたレジストリが異なるバイト列を配信すること | *設計上は*防御されています — インデックスがダイジェストに副署名し、デーモンが再ハッシュします — **しかし発効していません**: ルートは provisioned 状態です(`registry/v1/root.json`、デーモンにコンパイルされている同じ 2 つの鍵)が、それらが署名するカタログインデックスは今も未署名です |
| すでにインストール済みの、撤回されたバージョン | 仕様化されているが、未署名の撤回リストは拒否されるため、今日は強制されていません |
| 別のローカルプロセスがあなたのプラグインのケーパビリティサーバーに呼び込むこと | **防御されています。** デーモンはすべての呼び出しで spawn トークンを提示し、`ASTRA_PLUGIN_CAPABILITY_AUTH=require` を設定するため、SDK はそれのない呼び出しを拒否します。ヘッダーを送るには古すぎるデーモンの下では、SDK は `warn` のままです — 間違ったトークンは拒否されますが、欠落しているものは受け入れられます — それ以外に取れる手段がないためです |
| プラグインが自分のマニフェストを編集して自分のパーミッションを広げること | **ティア 1 と 2 では防御されています** — 付与はデーモンが所有する信頼レコードから来るのであって、マニフェストからではありません。**ティア 3 では防御されていません**: サイドロードされたディレクトリではマニフェストそのものが付与であり上限がないため、自分のファイルを編集することで語彙内のすべてのパーミッションを取得できます |
| 手動で仕込まれたサイドロードマーカー | 防御されています。デーモンは自分が書いていないマーカーを拒否します |

## ユーザー向けに、1 段落で

Astra の中からインストールしてください。ストア経由の経路はアーティファクト
をダイジェストで固定し、検証失敗はオーバーライドできない強制ブロックです。
誰かが `.astraplugin` ファイルを送ってきた場合、それをインポートすること
はその人物についてのあなた自身の判断であり、ファイルが何を要求していようと
4 つのパーミッションは拒否されます。誰かが開発者モードを有効にしてフォルダ
を Astra に指定するよう言ってきたなら、その人はあなたに、あなた自身として
未署名のコードを実行するよう頼んでいるのです。

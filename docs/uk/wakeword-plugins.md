# Плагіни слова-активатора

> Переклад. Джерело істини — [docs/en](../en/wakeword-plugins.md); за розбіжності відповідає англійська версія.

Плагін слова-активатора оголошує `wakeword = true` у розділі `[capabilities]`
свого `plugin.toml`. Astra показує встановлені плагіни з цією можливістю в
розділі **Голос → Слово-активатор**. Вибір і його налаштування зникають, коли
плагін видаляють. Плагіну не потрібна окрема сторінка чи внесок в інтерфейс.

## Створіть новий детектор

Візьміть поточний CLI і новий вихідний каталог:

<!-- doctest: cli -->
```bash
astra-plugin new my-wakeword --lang rust --template blank --capabilities wakeword --output ./my-wakeword
```

`--lang` може бути також `python` або `typescript`. Шаблону для слова-активатора
поки немає. Порожня заготовка Rust містить сторонній інструмент `hello` і його
тест: замініть обидва. Залиште `wakeword = true` єдиною можливістю, якщо плагін
справді не обслуговує щось іще. `astra-plugin check` знайде розбіжність між
маніфестом і скомпільованим бінарником.

Демон надсилає три описані нижче виклики через `CallFromUi`, навіть плагіну, який
оголошує лише `wakeword`. Це повторне використання транспорту; воно не вимагає ні
`ui_contributions`, ні iframe, ні `push_to_ui`. Загальні таблиці хуків відносять
`CallFromUi` до інтерфейсу, бо спочатку він саме для цього.

У Rust реалізуйте хук SDK `handle_ui_call(&self, ctx: &PluginContext,
method: &str, params_json: &str) -> Result<String, ToolError>` або використовуйте
методи `#[ui_call]` (з `#[ui_call(name = "process-audio")]` і
`#[ui_call(name = "reset-audio")]` для імен із дефісом); кожному методу
`#[ui_call]` потрібен doc-коментар `///`, інакше макрос відмовиться його
компілювати. Поставте `#[astra::plugin(capabilities = "wakeword")]` на блок impl
(заготовка вище вже це робить): інакше автоматичне виведення з `#[ui_call]`
оголосить `ui_contributions`, а це розходиться з маніфестом. Спрямовуйте
`status`, `reset-audio` і `process-audio` в один екземпляр детектора, чий буфер
кадрів зберігається між викликами. Повертайте JSON-рядки у формах відповіді,
показаних нижче.
У Python використовуйте обробники SDK `@ui_call`; у TypeScript —
`ui: { contributions: [], onCall: { ... } }` із трьома іменами методів.
Ці обробники не створюють видимої сторінки інтерфейсу.
Точку входу, доступ до конфігурації та життєвий цикл описано в посібниках SDK
для [Rust](4-sdk/rust.md), [Python](4-sdk/python.md) і
[TypeScript](4-sdk/typescript.md).

Свої налаштування плагін передає через наявну JSON Schema у `[config]`. Astra
показує ці поля в розділі «Голос», лише поки вибрано цей плагін, і зберігає їх
через `UpdatePluginConfig`. Підтримуються рядкові, числові, булеві властивості та
переліки. Рядок із `"format": "password"` стає полем пароля; `"format": "file"`
(або `"x-astra-field-type": "file_picker"`) пропонує вибір локального файлу.
`"x-astra-field-type": "slider"` і `"textarea"` обирають ці елементи керування
для числових і рядкових властивостей. Налаштований шлях читає сам плагін; формату
моделі ключового слова Astra не визначає.

Протокол 1 використовує для трьох методів автентифікований канал
запит/відповідь `CallFromUi`. Це внутрішній виклик демона; ні iframe, ні сторінка
не створюються.

| Метод | JSON запиту | JSON відповіді |
|---|---|---|
| `status` | `{}` | `{"ready": true}` або `{"ready": false, "message": "…"}` |
| `process-audio` | `{"pcm_base64": "…"}` | `{"detected": false}` або `{"detected": true}` |
| `reset-audio` | `{}` | `{}` |

`pcm_base64` містить моно-PCM 16 кГц, знаковий, 16 біт, little-endian. Astra
надсилає по 100 мс (1600 відліків) за виклик. Якщо детектор має іншу довжину
кадру, плагін мусить зберігати відліки між викликами. `reset-audio` відкидає це
збережене аудіо та проміжний стан розпізнавання в моделі, коли Astra скидає шлюз
активації. Декодуйте Base64, відхиляйте зіпсований PCM і PCM непарної довжини,
перетворюйте кожну пару байтів little-endian на `i16` і подавайте відліки в
детектор по черзі. Не вважайте кожен блок у 100 мс завершеною фразою. Кожен
виклик має строк дві секунди; аудіоцикл використовує обмежену чергу й ніколи не
чекає на плагін.
`astra-plugin test` викликає всі три методи й перевіряє форму їхніх
JSON-відповідей, зокрема блок аудіо з самих нулів, поки плагін, можливо, не
налаштований. Цей тест не перевіряє, що вибране ключове слово розпізнається.
Перед постачанням завантажте робочу модель і перевірте `status.ready = true`;
програйте кілька записів фрази-активатора через кілька викликів по 100 мс; і
програйте тишу, фоновий шум і звичайне мовлення як негативні випадки.
Переконайтеся, що `reset-audio` скидає недоказану фразу і що після скидання
розпізнавання працює. Потім установіть плагін або сайдлоадніть його, виберіть у
**Голос → Слово-активатор** і переконайтеся, що Astra починає слухати й
прокидається на фразу. Неналаштована модель має повідомляти `ready: false` з
корисним повідомленням.

Astra перевіряє `status.ready`, перш ніж почати слухати. Якщо вибраного плагіна
немає, він зупинений або не готовий, прослуховування відмовляє (fail closed), а
не перетворюється мовчки на безперервне розшифрування. Вибір під час роботи
задається через `voice.wake_word_mode = "plugin__<id>"`, де дефіси в ID плагіна
замінено підкресленнями, як і в ID провайдерів у плагінів STT і TTS.
Повідомляйте `ready: true`, лише коли детектор і його налаштована модель можуть
обробляти аудіо; самої наявності шляху до файлу недостатньо.

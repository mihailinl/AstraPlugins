# Дозволи

> Переклад. Джерело істини — [docs/en](../../en/3-reference/permissions.md); за розбіжності відповідає англійська версія.

Що дає кожен id з `[permissions]`, чого це коштує користувачу, і як написати
`reason`, який варто читати.

Це сторінка для авторів. Нормативні правила — видачі, стелі,
`permissions_hash`, точна семантика відмови — в
[`spec/permissions.md`](../spec/permissions.md). Згенерована таблиця того,
який RPC закриває кожен id, — в [`reference/manifest.md`](../reference/manifest.md)
і [`reference/parity.md`](../reference/parity.md), обидві виведені з
`spec/hooks.yaml` і звірені з власною таблицею демона правилом паритету R6.

## Форма цього

`[capabilities]` каже, що демон може викликати **всередині** вашого плагіна.
`[permissions]` каже, які RPC хоста ваш плагін може викликати **назовні**.
Два питання, два розділи; можливість ніколи не передбачає дозвіл.

Три властивості, кожна з яких когось та здивує:

1. **За замовчуванням усе заборонено.** Відсутність розділу `[permissions]`
   означає відсутність RPC хоста понад стартову четвірку.
2. **Оголосити — означає попросити, а не отримати.** Ваш маніфест — це
   запит. Виданий набір обчислює демон, виходячи з того, звідки плагін
   з'явився, і для встановленого чи імпортованого плагіна зберігає його там,
   куди плагін не може писати, — сам маніфест лежить у каталозі плагіна,
   який плагін може редагувати. **Сайдлоадинг це перевертає**: для каталогу з
   вихідним кодом у режимі розробника маніфест *і є* видача, що
   перечитується при кожному завантаженні, без стелі. Саме це робить робочим
   цикл розробки, і саме тому сайдлоадинг — інструмент розробника, а не шлях
   встановлення.
3. **Невідомий id зберігається і залишається бездіяльним.** Нові id
   виходять разом з новими версіями Astra, тож старіший демон зберігає ключ,
   якого не розпізнає, замість того щоб відхилити ваш маніфест. Він нічого
   не дає. `astra-plugin check` попереджає — одруківку неможливо відрізнити
   від прямо сумісного id на етапі розбору, тому це попередження, а не
   помилка, а `--strict` перетворює його на неуспішний вихід:

   <!-- doctest: output from="astra-plugin check --strict ." unrun="needs a plugin project in the working directory; re-run it in your own plugin" -->
   ```
     WARN: Unknown permission 'read_the_users_mail'. This Astra grants nothing for it. Valid: fire_trigger, subscribe_events, set_variable, send_chat_message, push_to_ui, set_theme_contribution, dom_access, client, read_ai_settings, speak, read_user_identity, receive_attachments, request_settings_change, propose_commands
     FAILED: 1 warning(s), and --strict treats warnings as errors
   ```

   Аркуш згоди на встановлення в Astra показує той самий id під власною
   міткою `permission.unrecognised`, тож він не губиться мовчки і на вході
   теж.

## Чотири виклики, яким нічого не потрібно

| RPC | Чому безкоштовний |
|---|---|
| `Register` | Рукостискання. Плагіна ще немає, щоб у нього були дозволи |
| `PluginLog` | Запис у власний лог |
| `GetPluginSelfConfig` | Читання власних налаштувань |
| `GetDaemonInfo` | `version`, `state`, `grpc_port`, `language` — усе це вже було у відповіді на реєстрацію |

Те, що `GetDaemonInfo` безкоштовний, — рішення, а не недогляд: чекбокс, який
нічого не захищає, — це те, як користувачі звикають ставити галочки не
дивлячись.

## Чотирнадцять id

| Id | Закриває | Свій чекбокс | Відхиляється для локального імпорту | Що дозволяє |
|---|---|---|---|---|
| `fire_trigger` | `FireTrigger` | ні | ні | Запускати збережені автоматизації користувача |
| `subscribe_events` | `SubscribeEvents` | ні | ні | Отримувати події демона — **бере список дозволених `types`** |
| `set_variable` | `SetVariable` | ні | ні | Писати в контекст змінних демона, у власному просторі імен |
| `send_chat_message` | `SendChatMessage` | **так** | **так** | Керувати ходом ШІ, наче говорив сам користувач |
| `push_to_ui` | `PushToUi` | **так** | ні | Надсилати подію у свої власні панелі |
| `set_theme_contribution` | `SetThemeContribution` | **так** | **так** | Переоформити весь застосунок |
| `dom_access` | — (поверхня) | **так** | **так** | Виконувати свій код всередині вікна Astra, з доступом до бесід та інтерфейсу будь-якого іншого плагіна |
| `client` | — (поверхня) | **так** | **так** | Бути фронтендом чату з власною сесією |
| `read_ai_settings` | `GetAiSettings` | ні | ні | Читати провайдера, модель і адресу чату користувача — але не ключ |
| `speak` | `Speak`, `StopSpeaking` | **так** | ні | Вимовляти свої слова вголос голосом Astra і зупиняти їх |
| `read_user_identity` | `GetUserIdentity` | ні | ні | Читати псевдоніми цього встановлення й акаунта, у який виконано вхід, створені лише для твого плагіна |
| `receive_attachments` | — (доставка) | **так** | ні | Отримувати зображення, які людина додала, в інструменті, що їх просить |
| `request_settings_change` | `RequestSettingsChange` | ні | ні | Попросити людину змінити налаштування, яке може змінювати асистент, на картці, на яку вона відповідає |
| `propose_commands` | `ProposeCommand` | **так** | ні | Запропонувати людині зберегти команду, яку вона зберігає з аркуша Workshop в Astra |

`dom_access` і `client` не закривають жоден RPC, і в цьому суть: це
**поверхні**. `dom_access` визначає, чи рендериться UI-внесок як скрипт у
вікні Astra, чи як ізольований iframe; `client` — це стеля того, чим плагін
взагалі може бути. Їх відхиляють там, де видається сама поверхня, а не на
шлюзі виклику. `receive_attachments` теж не закриває жоден RPC, але з
іншого боку: викликати тут нічого. Він вирішує, що Astra *надсилає* одному з
твоїх інструментів — [див. нижче](#отримувати-зображення-які-додала-людина).

`dom_access` додатково отримує другий екран згоди. Якщо ви тягнетеся за
ним, спершу прочитайте [модель безпеки](../1-orientation/security.md) і
переконайтеся, що `push_to_ui` у власну панель не вирішить задачу.

## Аргументи

Два id приймають аргументи, і обидва звужують те, що ви отримуєте.

<!-- doctest: toml-manifest -->
```toml
[plugin]
id = "meeting-notes"
name = "Meeting Notes"
version = "0.1.0"
license = "MIT"
author = "You"

[entry]
command = "bin/meeting_notes"

[capabilities]
tools = true
event_handlers = true

[permissions]
subscribe_events = { types = ["command_completed", "state_changed"], reason = "Notices when a recording command finishes so it can write the summary" }
set_variable = { scopes = ["plugin"], reason = "Stores the id of the note it just wrote so your commands can open it" }
fire_trigger = { reason = "Fires meeting_summarised when a summary is ready" }
```

- **`subscribe_events.types` — це список дозволених, який застосовує демон**
  — а не фільтр, який надсилає ваш плагін. Без нього кожен підписник
  отримував кожну подію, включно з `speech_recognized`, яка несе
  транскрипти користувача. Порожній список не дозволяє нічого.
- **`set_variable.scopes`** — це `"plugin"`, `"session"` або `"persistent"`.

## Читання налаштувань ШІ користувача

Плагін, який сам звертається до моделі користувача — власний асистент, підсумовувач, — мусить знати, якого провайдера, яку модель і яку адресу обрав користувач. **Питай про це Astra; ніколи не читай файли Astra.** Оголоси `read_ai_settings` і виклич `GetAiSettings` (`get_ai_settings()` у Rust і Python, `getAiSettings()` у TypeScript):

| Поле | Що це |
|---|---|
| `provider` | Ідентифікатор провайдера чату. Збережена користувачем адреса — це `openai_compatible`; власний сервіс Astra — `astra` |
| `model` | Ідентифікатор моделі чату |
| `api_base_url` | Адреса. Userinfo, query і fragment прибрано; шлях віддається так, як його налаштувала людина (якщо ретранслятор кладе токен у шлях, ти його отримаєш). Для `astra` порожньо: його адресу викликати не тобі |
| `is_loopback` | Адреса розташована на цій машині (`127.0.0.0/8`, `::1`, `localhost`) — локальна модель |

Ключа API тут ніколи немає, як і інших збережених адрес користувача, системного промпту та будь-якої ролі, окрім чату. Плагін, якому потрібен ключ, просить його в користувача у власному `[config]` (познач його секретним). Дозвіл не високоризиковий і не відхиляється для локального імпорту: це чесний шлях до цих відомостей, а ціна вища, ніж у читання `settings.json`, штовхала б плагіни не туди. Читання власних файлів Astra — те, що шукає ручна перевірка під час публікації. Astra старша за цей виклик відповідає `UNIMPLEMENTED`.

## Говорити голосом Astra

Плагін, якому є що оголосити — таймер, завершена збірка, отримане повідомлення, — може попросити Astra сказати це. Оголоси `speak` і виклич `Speak` (`speak(text)` у Rust і Python, `ctx.speak(text)` у TypeScript).

`speak` — **високоризиковий** дозвіл: твої слова звучать голосом Astra, ніби їх сказала Astra, тому він має свій чекбокс згоди. Для локального імпорту він не відхиляється: оголосити щось уголос — звичайне бажання плагіна, а рішення — це чекбокс. Окрім видачі, `Speak` потребує **акаунта з доступом до Astra** і **увімкненого озвучення відповідей** у людини; поки Astra заблокована, виклик відхиляється.

Виклик триває стільки ж, скільки мовлення, і відповідає тим, що з ним сталося:

| Результат | Що це означає | Що робити |
|---|---|---|
| `SPOKEN` | Його почули | Нічого |
| `STOPPED` | Тиші попросили до того, як воно закінчилося: wake-word, вимкнене озвучення відповідей, «Стоп», твій власний `StopSpeaking` | Нічого — **це не помилка**. Не повторюй без прохання |
| `NOT_SPOKEN` | Воно не прозвучало; `error` (той самий `PluginError`, що несе фрагмент чату) каже чому | Дивись код нижче. Ніщо відхилене не стає в чергу |

| `error.code` | Коли |
|---|---|
| `PLUGIN_ERROR_BAD_ARGUMENTS` | Текст порожній після видалення невидимих символів або довший за **300 символів** (`speak_text_max_chars` у `spec/limits.yaml`). Довший текст відхиляється, а не обрізається |
| `PLUGIN_ERROR_RATE_LIMITED` | Твій час мовлення вичерпано. Він рахується в символах — **450 одразу, потім 3 на секунду**, кожен виклик коштує щонайменше 20, — і `retry_after_ms` каже, коли знову з'явиться місце |
| `PLUGIN_ERROR_UNAVAILABLE` | Людина вимкнула голос Astra, Astra заблокована, голосу немає або черга мовлення не змогла його прийняти. Покажи натомість текст; не проси людину щось змінювати |

Твої слова стають у чергу за твоїми ж попередніми, на окремій смузі, тож вони ніколи не перебивають відповідь Astra. `StopSpeaking` зупиняє все, що ти просив сказати, — і те, що звучить, і те, що чекає в черзі, — і нічого більше; він ділить дозвіл `speak` і працює незалежно від того, чи виконано вхід. Ліміти належать демону: SDK експортують `SPEAK_TEXT_MAX_CHARS`, щоб ти міг показати лічильник, і самі нічого не перевіряють. Astra старша за цей виклик відповідає `UNIMPLEMENTED`.

## Знати, хто користується Astra

Плагіну, що обмежує використання на людину чи на машину — пробний період, квота, ліцензія, — потрібен стабільний id для кожної. **Питай про це Astra; ніколи не читай серійний номер обладнання чи файли Astra.** Оголоси `read_user_identity` і виклич `GetUserIdentity` (`get_user_identity()` у Rust і Python, `ctx.getUserIdentity()` у TypeScript):

| Поле | Що це |
|---|---|
| `install_id` | Це встановлення Astra: те саме після перезапусків і оновлень Astra та твого плагіна, інше на іншому встановленні. Порожньо, поки в Astra ще немає ключа встановлення |
| `signed_in` | Людина увійшла в Astra |
| `authorized` | …і її акаунт має доступ до Astra |
| `account_id` | Акаунт, у який виконано вхід: той самий на кожному пристрої, де людина входить. Порожньо, якщо не `authorized` |

Обидва id — **псевдоніми, створені лише для твого плагіна**: інший плагін читає для тієї самої людини й тієї самої машини інші id, тож два плагіни не можуть пов'язати за ними свої записи. Це справджується для плагінів, що чесно користуються цим API: нативний код плагіна може прочитати файли Astra. Жоден не є секретом, і жоден ніколи не є власним id акаунта, ім'ям чи email людини або серійним номером обладнання. Дозвіл не високоризиковий і не відхиляється для локального імпорту: це чесна альтернатива серійному номеру машини, а висока ціна штовхнула б плагін назад до нього. Astra старша за цей виклик відповідає `UNIMPLEMENTED`.

**`auth_changed` звужено відповідно** (Astra, 2026-11-12). Плагін, якому видано подію `auth_changed`, раніше отримував власний id акаунта, відображуване ім'я людини та її тариф. Тепер він отримує `authenticated`, `authorized`, `timestamp` і `account_id` — той самий псевдонім, що віддає `GetUserIdentity`, і `""`, якщо в тебе немає `read_user_identity` або акаунт не має доступу до Astra. `user_id` і `user_name` і далі надходять, як `null`, а `subscription_tier` — як `""`, щоб парсер, написаний під стару форму, далі розбирав; жодне з них більше не несе значення.

## Отримувати зображення, які додала людина

Інструмент, що працює із зображенням — прочитати чек, визначити рослину, описати фото, — може попросити зображення, які людина додала до повідомлення, на яке зараз відповідає Astra. **Жоден випуск Astra поки цього не робить:** демон надсилає їх, лише якщо зібраний з build feature `plugin-provider-slots`. Будь-яка інша Astra ігнорує прохання, і твій інструмент зображень не отримує.

Потрібні дві речі. Оголоси `receive_attachments` у `[permissions]` і познач кожен інструмент, якому потрібні зображення; потім читай їх у його обробнику:

| SDK | Позначити інструмент | Прочитати зображення |
|---|---|---|
| Rust | `#[tool(wants_attachments)]` або `ToolDef::new(…).with_attachments(true)` | `ctx.attachments()` |
| Python | `@tool("…", wants_attachments=True)` або `ToolDef(…, wants_attachments=True)` | `current_attachments()` |
| TypeScript | `wantsAttachments: true` у `tool({…})` або на `ToolDef` | `ctx.attachments` або `currentAttachments()` |

Кожне зображення несе `mime_type` (`mimeType` у TypeScript), `data` — байти — і `filename`, голе ім'я, під яким його додали, ніколи не теку. Інструмент, що їх не просив, читає порожній список, як і будь-який виклик без зображень.

Astra передає зображення виклику, лише коли виконано все це:

- інструмент оголосив `wants_attachments` у своїй відповіді на `ListTools`;
- твій плагін має `receive_attachments`;
- виклик зроблено, поки Astra відповідала на повідомлення, яке людина надіслала в бесіді, — invocation виклику називає цю бесіду. Ніколи в report wake, в ШІ-кроці команди чи в ході субагента і ніколи, поки Astra утримує хід заради команди з Workshop, яку людина не схвалила.

Надходить лише те, що було додано до **цього одного повідомлення**: ніколи зображення з ранішої частини бесіди, ніколи зображення, створене інструментом, і ніколи зображення, яке назвала модель. Не більше **4** (`image_input_max_images` у `spec/limits.yaml`) і 20 MiB загалом, зберігаються найновіші, у тому порядку, в якому їх додали; зображення, яке не вдається прочитати, не надсилається ніколи. Якщо якісь не надіслано — їх більше, ніж вміщується, або твій плагін не має видачі, — про це кажуть **моделі** після твого результату; твій інструмент просто отримує менше або нічого.

Зараз поле введення чату Astra зменшує кожне додане зображення щонайбільше до 768 пікселів і перекодовує його в JPEG, зберігаючи початкове ім'я файлу, — саме це й отримує твій інструмент. Орієнтуйся на `mime_type`, а не на розширення в `filename`.

Один виклик може нести до 20 MiB зображень — більше, ніж типовий ліміт приймання gRPC, 4 MiB. Capability-сервери трьох SDK приймають до 64 MiB (`plugin_max_message_bytes`); плагін, що обслуговує протокол без SDK, мусить підняти ліміт приймання свого сервера вище 4 MiB.

`receive_attachments` — **високоризиковий** дозвіл: фотографії людини потрапляють у код, який не належить Astra, тому він має свій чекбокс згоди. Для локального імпорту він не відхиляється — рішення ухвалює чекбокс, як і для `speak`.

## Попросити людину змінити налаштування

Плагін, що має справжню причину хотіти, щоб одне з налаштувань Astra змінилося, — модель, під яку налаштовано його інструменти, голос, що йому пасує, — **просить**, а людина вирішує на картці. Ніколи не пишіть `settings.json` Astra самі й ніколи не позичайте для цього власну сесію Astra: так ви змінюєте Astra людини в неї за спиною, і ручна перевірка під час публікації шукає саме це. Оголосіть `request_settings_change` і викличте `RequestSettingsChange` (`request_settings_change(changes, reason)` у Rust і Python, `ctx.requestSettingsChange(changes, reason)` у TypeScript). **Жоден реліз Astra поки що на нього не відповідає.** Astra, зібрана з функцією збірки `plugin-requests`, приймає запити; новіша Astra, зібрана без неї, відповідає `REFUSED` з кодом `not_compiled`; у старішої — сьогодні це будь-який реліз — виклик завершується помилкою `UNIMPLEMENTED`: це помилка, а не результат.

Кожна зміна — шлях налаштування через крапку й бажане значення у вигляді JSON; SDK серіалізують значення за вас. Просити можна лише про ті налаштування, які може змінювати сам асистент, — голос, модель ШІ, мову; ніколи режим дозволів, ключ чи Tool Search, — і кожне значення перевіряється точно так само, як власна зміна асистента. Картка називає ваш плагін, показує кожне налаштування, яким воно є і яким стане, і ваш `reason` вашими словами. Змінюються всі або жодне, і змінюється саме те, що показала картка.

**Виклик триває, доки людина не відповість або картка не спливе** — це тайм-аут підтвердження Astra, щонайменше 30 секунд, 120, якщо людина його не змінювала. SDK не ставлять на нього власного дедлайну. Ніколи не чекайте на нього на шляху, що має відповісти швидко, наприклад у виклику інструмента, на який чекає модель.

| Результат | Що це означає | Що робити |
|---|---|---|
| `APPLIED` | Людина дозволила; налаштування тепер містять те, про що ви просили | Нічого |
| `UNCHANGED` | Вони вже це містили. Нікого не питали | Нічого |
| `DECLINED` | Людина сказала «ні» — зараз або раніше, коли ваш плагін хотів змінити одне з цих налаштувань. Astra знову спитає про таке налаштування, лише коли воно зміниться іншим шляхом, або після перезапуску | Продовжуйте з тим, що в людини є. **Не питайте знову без приводу** |
| `TIMED_OUT` | Ніхто не відповів, доки картка не спливла (відсутність відкритого вікна теж сюди належить) | Спитайте пізніше, коли людина буде поруч |
| `REFUSED` | Не спитали або не застосували: `code` каже чому, `refused_path` називає налаштування, якщо йдеться про нього, а `error` — це `PluginError` | Дивіться код нижче |

| `code` | Коли |
|---|---|
| `not_compiled` | Ця Astra не приймає запитів: її зібрано без функції `plugin-requests` |
| `locked` | Astra заблокована паролем |
| `invalid` | Немає змін, шлях двічі, значення — не JSON, або більше, ніж картка може показати повністю |
| `too_many` | Понад **8** змін (`settings_change_max_changes` у `spec/limits.yaml`) |
| `reason_too_long` | Причина, довша за **140 символів** (`settings_change_reason_max_chars`). Її показують повністю, тож вона відхиляється, а не обрізається |
| `busy` | Один із ваших запитів уже чекає на людину: одна картка на плагін водночас |
| `rate_limited` | **Сплеск із двох запитів, потім один на дві хвилини**; `error.retry_after_ms` каже, коли знову буде місце |
| `not_assistant_editable` | Шлях, який асистентові змінювати не можна |
| `invalid_value`, `unknown_choice` | Значення, якого налаштування не може містити, або варіант, якого воно не пропонує |
| `needs_api_key`, `needs_stt_provider`, `provider_unreachable` | Зміна залишила б Astra без того, що їй потрібно: ключа для цього провайдера ШІ, розпізнавача мовлення, провайдера, що відповідає |
| `stale` | Налаштування змінилися, поки картка була відкрита, тож дозволене людиною — не те, що було б записано. Нічого не записано |
| `stopped` | Повноваження вашого плагіна закінчилися раніше — його зупинили, вимкнули або відкликали, або акаунт утратив доступ до Astra |
| `write_refused` | Налаштування не вдалося записати |

Поточні значення ніколи не повертаються: ваш плагін дізнається лише результат. Ліміти — справа демона: SDK експортують `SETTINGS_CHANGE_MAX_CHANGES` і `SETTINGS_CHANGE_REASON_MAX_CHARS` і самі не перевіряють жодного. Окрім дозволу, виклику потрібен **акаунт із доступом до Astra**; відсутність дозволу чи акаунт без доступу до Astra — це невдалий виклик, як у будь-якого виклику хоста, а не результат. Це не високоризиковий дозвіл, і він не відхиляється під час локального імпорту: кожен запит — картка, на яку людина відповідає, тож згоду питають щоразу. Astra, старша за цей виклик, відповідає `UNIMPLEMENTED`.

## Запропонувати людині команду

Плагін, якому є що дати, — корисну автоматизацію на кшталт «читай мені новини, коли я кажу „доброго ранку"», зібрану з його власних дій, — **пропонує** її, а людина вирішує. Плагін не може сам записати команду до бібліотеки людини: `CommandService` закритий для сесії плагіна, і до цього виклику плагін міг лише описати команду в чаті й сподіватися, що людина збере її заново. Оголосіть `propose_commands` і викличте `ProposeCommand` (`propose_command(key, command, reason)` у Rust і Python, `ctx.proposeCommand(key, command, reason)` у TypeScript). **Жоден реліз Astra поки що на нього не відповідає.** Astra, зібрана з функцією збірки `plugin-requests`, приймає пропозиції; новіша Astra, зібрана без неї, відповідає `REFUSED` з кодом `not_compiled`; у старішої — сьогодні це будь-який реліз — виклик завершується помилкою `UNIMPLEMENTED`: це помилка, а не результат.

Команда — це **одна переносна команда**: те, що лежить у `commands[]` файлу `.astra`. Найпростіше зібрати її в Astra, експортувати зі сторінки команд і постачати файл разом із плагіном; у кожному SDK є помічник, який розбирає такий файл на команди (`commands_from_astra_file` у Rust і Python, `commandsFromAstraFile` у TypeScript), кожну без полів, що належать одному встановленню (`id`, `enabled`, тека, походження). Демон читає команду власним читачем Workshop — строгий JSON, лише відомі типи дій і тригерів, ці локальні поля відкидаються, тож плагін не може ні підробити, звідки команда, ні ввімкнути її, — і команда може використовувати вбудовані дії та тригери Astra і **власні** — вашого плагіна, але ніколи — чужого (`foreign_plugin`). Серед вбудованих є shell-команда, натискання клавіш і операції з файлами: аркуш показує кожен крок із тим, що він може зробити, і саме на це погоджується людина.

`key` — власне ім'я команди у вашого плагіна: від 1 до 64 символів з `a-z`, `A-Z`, `0-9`, `.`, `_` і `-`. Той самий ключ, запропонований знову, — та сама команда, оновлена на місці (її id і тека зберігаються), щойно людина знову погодиться; запропонувати саме ту команду, що вже збережена під цим ключем, означає нікого не питати (`UNCHANGED`).

Astra пам'ятає менше, ніж здається, тож не пропонуйте просто всі команди під час кожного запуску:

- `DECLINED` пам'ятається лише до перезапуску Astra — після нього та сама пропозиція знову картка;
- команди, яку людина видалила, під її ключем більше немає, тож повторна пропозиція — нова, знову картка;
- команда, вимкнена під час видалення вашого плагіна, лишається вимкненою після перевстановлення, а та сама пропозиція відповідає `UNCHANGED`;
- `UNCHANGED` порівнює вашу пропозицію з тим, що було запропоновано й збережено під ключем, тож це й відповідь після того, як людина відредагувала збережену команду.

Запам'ятовуйте `SAVED` і `DECLINED` за ключем у власному стані плагіна, а під час запуску пропонуйте лише ключі, на які у вас немає відповіді, — і команду, яку ви змінили.

Людина бачить картку з назвою вашого плагіна й команди, з вашим `reason` вашими словами і двома варіантами: «Переглянути» і «Відхилити». **Команда зберігається лише з аркуша Workshop в Astra** — кожен тригер із повним значенням, кожен крок із тим, що він може зробити, і перемикач увімкнення, — ніколи простим «Дозволити», і зберігається саме те, що показав аркуш. Збережена команда має мітку вашого плагіна; видалення плагіна вимикає його команди.

**Виклик триває, доки людина не відповість або картка не спливе** — це тайм-аут підтвердження Astra, щонайменше 30 секунд, 120, якщо людина його не змінювала. SDK не ставлять на нього власного дедлайну. Ніколи не чекайте на нього на шляху, що має відповісти швидко, і **пропонуйте по одній команді**: друга пропозиція, поки одна ваша чекає, відхиляється як `busy`, навіть така, що була б `UNCHANGED`.

| Результат | Що це означає | Що робити |
|---|---|---|
| `SAVED` | Людина зберегла її; `enabled` каже, чи ввімкнена команда після збереження (Astra може зберегти її вимкненою) | Запам'ятайте це |
| `UNCHANGED` | Те, що збережено під цим ключем, прийшло саме з цієї пропозиції — і після того, як людина його відредагувала. Нікого не питали | Нічого |
| `DECLINED` | Людина сказала «ні» — зараз або раніше, саме цій команді (доки Astra не перезапуститься) | Запам'ятайте це. **Не пропонуйте її знову без приводу** |
| `TIMED_OUT` | Ніхто не відповів, доки картка не спливла (відсутність відкритого вікна теж сюди належить) | Запропонуйте пізніше, коли людина буде поруч |
| `REFUSED` | Не спитали або не зберегли: `code` каже чому, а `error` — це `PluginError` | Дивіться код нижче |

| `code` | Коли |
|---|---|
| `not_compiled` | Ця Astra не приймає пропозицій: її зібрано без функції `plugin-requests` |
| `locked` | Astra заблокована паролем |
| `invalid_key` | Ключ, що не складається з 1–64 символів з `a-z`, `A-Z`, `0-9`, `.`, `_` і `-` |
| `reason_too_long` | Причина, довша за **140 символів** (`propose_command_reason_max_chars` у `spec/limits.yaml`). Її показують повністю, тож вона відхиляється, а не обрізається |
| `too_large` | Понад **1 МіБ** JSON (`propose_command_max_bytes`) — власна межа команди Workshop |
| `invalid_command` | Це не команда, яку приймає читач Workshop; `error.message` зазвичай починається з його власного коду — `E_COMMAND_FORMAT`, `E_COMMAND_UNKNOWN_ACTION`, …, — але не тоді, коли саму картку неможливо показати (назва команди й ваша причина на неї не вміщаються) |

| `busy` | Одна з ваших пропозицій уже чекає на людину: одна картка на плагін водночас |
| `rate_limited` | **Сплеск із двох пропозицій, потім одна на дві хвилини**; `error.retry_after_ms` каже, коли знову буде місце. Пропозиція, за якої нікого не питають (`UNCHANGED`, запам'ятований `DECLINED`), нічого не витрачає |

Окрім дозволу, виклику потрібен **акаунт із доступом до Astra**; відсутність дозволу чи акаунт без доступу до Astra — це невдалий виклик, як у будь-якого виклику хоста, а не результат. `propose_commands` — **високоризиковий** дозвіл: збережена команда виконується пізніше, за своїми тригерами, як власна команда людини — її кроки, включно з вбудованими на кшталт shell-команди, виконуються без повторного питання, — тому в нього свій чекбокс згоди. Під час локального імпорту він не відхиляється: рішення — сам аркуш, щоразу. Astra, старша за цей виклик, відповідає `UNIMPLEMENTED`.

## Як написати reason

`reason` рендериться під власною міткою Astra для дозволу, візуально
підпорядковано, в лапках, простим текстом, з обмеженням у 140 символів, і
завжди з префіксом *«The author says:»*. Мітка належить Astra, мовою
користувача; reason — ваш. Ви не можете сформувати саму мітку, і це навмисно:
формулювання фіксуються в постачанні Astra і не повинні бути записуваними
через лістинг.

Хороший reason:

- **називає фічу, яку впізнає користувач**, а не API — *«Запускає тригер
  on_dice_roll, який ви налаштували»*, а не *«викликає FireTrigger»*;
- **каже коли**, якщо не завжди — *«лише поки триває запис»*;
- **не повторює мітку.** Astra вже її відрендерила;
- **не тисне.** Жодної терміновості, погроз, інструкцій користувачу. Аркуш
  згоди — останнє місце для винятку, і текст з bidi-перевизначеннями або
  з'єднувачами нульової ширини відхиляється там, де відображається дослівно.

| Замість | Пишіть |
|---|---|
| `"needs fire_trigger"` | `"Fires the trigger you configure when a roll completes"` |
| `"required for the plugin to work"` | `"Reads command-completion events so it can log the run"` |
| `"full access to the UI"` | `"Draws the timer in the panel this plugin adds to the sidebar"` |
| `"REQUIRED! Do not disable!"` | — вилучіть дозвіл, або скажіть, для чого він |

Дозвіл без правдоподібного reason — це дозвіл, який треба видалити з
маніфесту. Автоматично це ніхто не перевіряє; єдиний захист — людина, що
читає вашу заявку, і `astra-plugin check` скаже вам, коли ви оголосили
дозвіл, який не потрібен вашим можливостям.

## Що відбувається, коли дозволу бракує

Виклик повертається з `permission_denied`, з повідомленням, що називає
дозвіл **і** звідки взявся виданий набір. У тесті це можна інсценувати рівно
так:

<!-- doctest: rust-plugin test=1 -->
```rust
use astra_plugin_sdk::prelude::*;

#[derive(Default)]
struct Notifier;

#[astra::plugin]
impl Notifier {
    /// Announce that something happened.
    #[tool]
    async fn announce(&self, ctx: &PluginContext) -> Result<String, ToolError> {
        // Handle the denial rather than propagating it: a tool that returns an
        // error the model cannot act on is worse than one that says what it did.
        match ctx.host().fire_trigger("announced", "{}").await {
            Ok(()) => Ok("announced".into()),
            // `{e:#}` and not `{e}`: the host call fails with a short outer
            // message and the useful half — the permission id and where the
            // granted set came from — is in the cause chain.
            Err(e) => Ok(format!("could not fire the trigger: {e:#}")),
        }
    }
}

astra::main!(Notifier::default());

#[cfg(test)]
mod tests {
    use super::*;
    use astra_plugin_sdk::testing::Harness;

    #[tokio::test]
    async fn a_missing_grant_is_reported_not_hidden() {
        let h = Harness::new(Notifier::default()).start().await.unwrap();
        h.host().deny("fire_trigger");

        let answer = h.call_tool("announce", json!({})).await.unwrap();
        assert!(answer.contains("fire_trigger"), "{answer}");
    }
}
```

`astra-plugin doctor` відповідає на те саме питання про маніфест ще до того,
як ви його хоч раз запустите:

<!-- doctest: output from="astra-plugin doctor ." unrun="reports this machine's toolchains, daemon and config paths, so its output differs on every machine" -->
```
  [ok  ] Why is a host call coming back `permission_denied`?
         [permissions] grants: none. Every declared capability has the host rpc it needs.
```

## Звідки береться виданий набір

| Шлях встановлення | Видано |
|---|---|
| З каталогу, верифікований | те, що запросив маніфест, після згоди |
| Файл `.astraplugin`, імпортований вручну | маніфест, **зі стелею**: `send_chat_message`, `set_theme_contribution`, `dom_access`, `client` відхиляються безумовно |
| Сайдлоаднутий каталог з вихідним кодом, режим розробника увімкнено | маніфест, без стелі |
| `Untrusted` / `TamperDetected` / `Revoked` | нічого |
| Встановлено до появи записів довіри | маніфест, зі стелею як у імпортованого файлу |

Повна таблиця і обґрунтування:
[`spec/permissions.md` §4](../spec/permissions.md).

## Згода, з боку користувача

Дозволи згруповані за ризиком. Вісім високоризикових отримують кожен свій
чекбокс, і кнопка «Встановити» лишається неактивною, поки не позначено
кожен; `dom_access` отримує другий екран. Навмисно **немає введення-для-
підтвердження**: це патерн для незворотного знищення, а привчання
користувачів друкувати, щоб пройти його, знищує сигнал, який несе чекбокс.

При оновленні: дозволи, що не змінилися або звузилися, застосовуються
мовчки; дозволи, що **розширилися**, ставлять оновлення в чергу без
встановлення і лишають стару версію працюючою, поки користувач не розгляне
різницю. Відмова нічого не коштує.

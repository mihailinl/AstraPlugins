# Діагностика

> Переклад. Джерело істини — [docs/en](../../en/6-operate/troubleshooting.md); за розбіжності відповідає англійська версія.

Прив'язана до рядків, які насправді друкують CLI і демон. Якщо перед вами
помилка, шукайте на цій сторінці її фрагмент.

## Почніть звідси

<!-- doctest: cli -->
```bash
astra-plugin doctor
```

П'ятнадцять перевірок, кожна сформульована як питання, на яке відповідає.
Вона знає, який CLI ви використовуєте, який каталог конфігурації вона
визначила, чи доступний демон, які у вас тулчейни, чи розбирається ваш
маніфест, чи існує точка входу, чи покривають ваші дозволи ваші
можливості, чи правильний у вас блок `[platform]`, і чи закріплений ваш
workflow релізу. Кожен збій несе рядок `fix:`. У проєкті, який ви ще не
збирали, вона виходить з ненульовим кодом на одному з них — «Will the
daemon find something to start? … does not exist» — і це правильно:
бінарник ще ніхто не виробив.

## Проєкт не може розв'язати свій SDK

**`error: failed to select a version for the requirement astra-plugin-sdk = "^0.6"`**
**`ERROR: No matching distribution found for astra-plugin-sdk<0.6,>=0.5`**
**`error: No version matching "^0.5.0" found for specifier "astra-plugin-sdk" (but package exists)`**

Три мови, одна форма помилки — і відсутність SDK більше не є її причиною.
`astra-plugin new` закріплює `astra-plugin-sdk` `0.6` для Rust, `>=0.5,<0.6`
для Python і `^0.5.0` для TypeScript, а публічні реєстри несуть crates.io
**0.6.0**, PyPI **0.5.0** і npm **0.5.0**. Кожне з цих закріплень
розв'язується у свіжому проєкті без жодного налаштування, тож якщо у вас не
розв'язується, причина — між вашою машиною і реєстром:

- **Застарілий індекс, lock-файл або дзеркало, що не синхронізувалося.**
  Резолвер відповідає з кешованого вигляду реєстру, знятого до релізу, або з
  корпоративного проксі, який робить те саме. `cargo update -p
  astra-plugin-sdk`; `pip install --upgrade --no-cache-dir -r requirements.txt`;
  для npm — видалити `node_modules` і lock-файл та встановити заново.
  `cargo --offline` і `npm --offline` дають цю помилку за визначенням.
- **Хтось послабив межу.** Пін, відредагований до `0.5` (Rust) або `0.4`
  (Python, TypeScript), просить те, чого жоден реєстр за такого обмеження не
  пропонує. Поверніть пін із шаблону, а не розширюйте його далі: 0.6 — перший
  реліз Rust, чий `HostClient` прикріплює `x-session-token`, тож старіший SDK
  міняє цю помилку на `unauthenticated` при кожному виклику хоста — наступний
  розділ.

Ні `doctor`, ні `check` про це не згадають, тому що обидва читають
`plugin.toml`, а закріплення живе у файлі збірки самої мови.

## Плагін не запускається

**`Could not read /…/astra/daemon.token. Astra does not look like it is running — start the app first.`**
Рівно те, що там написано. `dev`, `logs` і встановлення потребують
запущеної Astra; `new`, `build`, `check`, `test`, `sign` і `publish` — ні.
Якщо Astra *запущена*, значить вона визначила інший каталог конфігурації,
ніж CLI, — порівняйте шлях, який друкує `doctor`, з тим, що показує Astra
у своїх налаштуваннях.

**Демон прибрав процес при старті.** Бюджет — `plugin_start_timeout_secs`
= **20 с** до першого рядка виводу. Python-плагін, що імпортує великий
ML-стек на рівні модуля, може в нього не вкластися; імпортуйте ліниво,
всередині того хука, якому це потрібно. `astra-plugin test` це вимірює і
друкує число:

<!-- doctest: output from="astra-plugin test . --no-build" unrun="starts a real plugin process and runs the conformance suite against it; needs a built plugin" -->
```
  [ok  ] the plugin says something before the daemon gives up: first line on stdout after 792.4µs
         (the daemon waits 20s, spec/limits.yaml plugin_start_timeout_secs)
```

**Плагін запускається і одразу падає.** Спершу перевірте `astra-plugin
logs -f`; якщо там взагалі нічого немає, процес падає до того, як SDK
встановить своє логування. Запустіть бінарник вручну — `astra-plugin dev
--standalone` робить це і каже, чого так зробити не можна.

**Помилки `HealthCheck` позначають плагін мертвим.** Вона виконується
кожні 15 с і не проходить через опціональний хелпер демона для
необов'язкових хуків: *будь-яка* помилка, включно з `UNIMPLEMENTED`,
означає «мертвий». Якщо ви перевизначили `health_check`, переконайтеся, що
вона не може кинути виняток.

## Виклик хоста повертається з `permission_denied`

Повідомлення називає дозвіл і звідки взявся виданий набір. Три причини, за
спаданням ймовірності:

1. **Ви його не оголосили.** `[permissions]` за замовчуванням забороняє
   все. Оголошення `[capabilities] event_handlers = true` не дає
   `SubscribeEvents`; це робить `[permissions] subscribe_events`.
2. **Користувач його не видав**, або шлях встановлення його обмежив. У
   [локально імпортованого файлу](../5-publish/local-install.md)
   `send_chat_message`, `set_theme_contribution`, `dom_access` і `client`
   відхиляються безумовно.
3. **Ви вийшли з облікового запису або застосунок заблокований.** Astra
   відхиляє RPC плагінів в обох станах, і CLI про це каже: *«Astra refuses
   plugin RPCs while signed out or locked — sign in and unlock the app,
   then try again.»*

`astra-plugin doctor` відповідає на пункт 1, нічого не запускаючи:

<!-- doctest: output from="astra-plugin doctor ." unrun="reports this machine's toolchains, daemon and config paths, so its output differs on every machine" -->
```
  [ok  ] Why is a host call coming back `permission_denied`?
         [permissions] grants: none. Every declared capability has the host rpc it needs.
```

## Виклик хоста повертається з `unauthenticated`

Кожен виклик `PluginHostService`, крім `Register`, зобов'язаний нести
токен сесії в `x-session-token`. Усі три SDK його прикріплюють — **починаючи
з 0.6 у Rust, 0.5 у Python і TypeScript**. Проти старішого SDK кожен
виклик хоста провалюється саме так, і тому межа залежності в заготовці не
опускається нижче.

`astra-plugin test` перевіряє це від початку до кінця:

<!-- doctest: output from="astra-plugin test . --no-build" unrun="starts a real plugin process and runs the conformance suite against it; needs a built plugin" -->
```
  [ok  ] every host call carried the session token: no host call was refused for want of `x-session-token`
```

## Сайдлоадинг відхиляється

**`Sideloading is disabled.`** `safety.allow_unsigned_plugins` вимкнений.
Прочитайте, [чого коштує його увімкнення](../5-publish/sideload.md),
перш ніж це робити.

**`Refusing sideload marker in …: this daemon never authorised a sideload of …`**
Хтось вручну підклав `sideload.json`. Це не працює відтоді, як демон почав
вести власний запис того, що він авторизував. Використовуйте
`astra-plugin dev`.

## Встановлення відхиляється

Кожен провал верифікації на шляху через каталог — це **жорсткий блок без
обходу**, і кожен називає, яка з двох речей сталася.

| Що ви бачите | Що це означає |
|---|---|
| Завантажений файл не збігається з тим, що підписав реєстр | `DIGEST_MISMATCH` — завантаження відкинуто. Повідомте про це |
| Astra не змогла верифікувати підпис каталогу плагінів | `SIGNATURE_INVALID` — магазин вимикається, а не відкочується до неверифікованих даних |
| Це оновлення прийшло з іншого репозиторію, ніж той, звідки ви встановлювали | `IDENTITY_CHANGED` — обходу немає ніколи. Лише видалення знімає закріплення |
| Плагін було відкликано | `REVOKED` — з порадою і видаленням в один клік. Файли ніколи не видаляються мовчки |
| Цей бандл для іншої платформи | `PLATFORM_UNSUPPORTED` |
| Цьому плагіну потрібна новіша Astra | `PROTOCOL_UNSUPPORTED` |
| Мережа, або невірний годинник | Можна повторити, і сформульовано саме так. Це ніколи не повинно виглядати як провал верифікації |

**`nothing here vouches for these bytes`** для локального файлу: встановіть
його зі сторінки плагінів натомість, або прочитайте про
[локальне встановлення](../5-publish/local-install.md), чого коштує імпорт.

Сьогодні ланцюг довіри заякорений **на одну ланку менше, ніж потрібно**:
кореневі ключі існують, і підписаний коренем `trust.json`, що делегує
ключ підпису індексу, тепер теж існує, але `registry/v1/index.json` і
`revocations.json` все ще несуть `"signatures": []`. Без підпису на
каталозі делегованому ключу нема чого перевіряти, тож каталог
класифікується як непідписаний, і відкликання не застосовується. Див.
[`spec/registry-index.md` §0.1](../spec/registry-index.md).

## Виклик інструмента провалюється так, що модель не може це виправити

Використовуйте правильний код; саме його читає модель.

| Код | Використовуйте, коли |
|---|---|
| `BAD_ARGUMENTS` | Повтор з іншими аргументами міг би спрацювати |
| `NOT_CONFIGURED` | Відсутнє налаштування — **і задайте `config_field`**, саме це перетворює помилку на посилання на конкретне поле |
| `UNAUTHORIZED` | Значення є, але було відхилене. Відрізняється від `NOT_CONFIGURED` |
| `RATE_LIMITED` | З `retry_after_ms`, коли його назвав вищерозташований сервіс |
| `UNAVAILABLE` / `TIMEOUT` | Тимчасово. Пізніший ідентичний виклик може спрацювати |
| `INTERNAL` | Баг. Модель нічого з цим не зробить |

`UNIMPLEMENTED` — це **не** помилка: вона означає «цього хука немає», і
демон читає її саме так. Повернути її, тому що впав ваш TTS, змусить
демона повірити, що у вас взагалі немає TTS. Повна таксономія:
[`reference/errors.md`](../reference/errors.md).

## `astra-plugin check` скаржиться

**`config.schema is not valid JSON`** або **`should have "type": "object" at
root`** — форма налаштувань генерується з цієї схеми.

**Невідомий ключ у `[capabilities]` валить весь маніфест.** Цей розділ —
єдине місце, де невідомі ключі відхиляються, тому що кожен ключ — це
булева ознака згоди, і одруківка інакше читалася б рівно як `false`.
`ui_panels` — класика: правильно `ui_contributions`, і три приклади з
постачання місяцями не оголошували взагалі нічого саме через це.

**Невідомий id у `[permissions]` зберігається, і про нього попереджають**,
а не відхиляють — нові id виходять разом з новими версіями Astra, а блок
дозволів хешується побайтово трьома реалізаціями, тож відкидання ключа
змусило б їх розійтися в тому, що було підписано.

`astra-plugin check --fix` застосовує те, що може довести, і повідомляє
про решту.

## CLI не друкує нічого корисного

`RUST_LOG` тепер працює — вона документувалася з 0.1 і була бездіяльною,
поки не встановили підписника:

<!-- doctest: cli -->
```bash
RUST_LOG=astra_plugin=debug astra-plugin check
RUST_LOG=debug astra-plugin build
```

Трасування йде в **stderr**, тож `--json` на stdout залишається чистим
єдиним документом.

## Коди виходу

| | |
|---|---|
| `0` | успіх |
| `1` | плагін або бандл неправильний |
| `2` | CLI не змогла виконати перевірку — відсутній файл, відсутній тулчейн |

Цей розподіл — несучий: workflow релізу, що ставиться до «бандл поганий» і
«я не зміг подивитися» однаково, поставить один з них.
